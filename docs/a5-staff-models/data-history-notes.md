# היסטוריית נתונים (`/admin/data-history`) - notes

מסך חדש בעיצוב רשימות A5 ליומן השינויים של המערכת (`AuditLog`: כל יצירה / עדכון / מחיקה של לקוח, הזמנה, תשלום, דגם, עובד...). הישן: `HistoryViewer` (ציר זמן של כל ה-100 האחרונים, בלי לדעת על מה השינוי).
קבצים: `app/components/history-lists/{DataHistoryA5,DataHistorySwitch,dataHistoryLogic,historyShared,history-lists.css}.js`, `lib/adminAuditList.js` (טהור), `lib/adminAuditListServer.js`, `lib/adminLogList.js` (טהור, משותף לשני היומנים),
`app/api/admin/data-history/{route,counts/route}.js`, `app/components/a5-print/pkSpecsHistory.js` (`auditLogDoc`), `app/admin/data-history/{page,LegacyDataHistoryPage}.js`. בדיקות: `scripts/test_a5_history_lists.mjs` (33), מדידה: `scripts/perf/history-lists-profile.mjs`.
הרכיב הישן `components/HistoryViewer.js` **לא שונה** (משותף לכרטיסי לקוח / הזמנה / דגם / עובד - נבדק ב-`git status` בבדיקה).

## מה המסך עושה
* שורה 1 = משפט אנושי: "הזמנה #53375 · עודכנה", "לקוח דוד כהן · נוצר", "פריט בהזמנה #28315 · אישור השכרה", "תשלום בהזמנה #7 · נמחק" (מגדר הרשומה: עודכנה / עודכן). **אף UUID לא מוצג** (AGENTS.md): מזהה ההזמנה = מספר ההזמנה; לקוח = שם; דגם = שם; פריט דגם = "שם הדגם (מידה)"; דיווח שגיאה = 8 תווים; ישות שנמחקה / בלי דף = סוג הרשומה בלבד.
* שורה 2: מתי (יום עברי + שעה), מי ביצע (או "מערכת"), כמה שדות שונו (רק כשיותר מאחד). אייקון הרשומה = סוג הישות (טולטיפ), מחיקה = פח.
* חץ פרטים: מתי / מי / סוג רשומה / הלקוח (בהזמנה) / **לפני ← אחרי לכל שדה** (תוויות שדה בעברית מ-`FIELD_TRANSLATIONS` של הרכיב הישן, ערכים: כן/לא, תאריך עברי, ₪, תוויות ערך מכונה) / "ועוד N שדות" / כפתור "פתיחת הרשומה" (הזמנה / לקוח / דגם / עובד / פריט דגם -> הדף הקיים). לחיצה על השורה פותחת את הכרטיס (בלי כרטיס - פותחת את הפירוט).
* סינון (חלון אחד): סוג רשומה (מהספירות, לפי ספירה יורדת), פעולה (יצירה / עדכון [כולל UPDATE_ORDER] / מחיקה / ביטול [CANCEL_*] / פעולה אחרת), עובד (30 הפעילים ביותר + "מערכת"), תקופה (היום / 7 / 30 ימים / שנה / טווח מותאם בחלון כהה עם לוח עברי). אפשרות בלי תוצאות מוסתרת.
* מיון: זמן (ברירת מחדל, החדש ראשון), סוג רשומה, פעולה, עובד, היקף השינוי; כל עמודת טבלה ממוינת (5 עמודות). חיפוש: בתוך פרטי השינוי (כמו הישן) + מספר הזמנה (גם מזהה הישות הפנימי של ההזמנה, שאליו כותבים השורות האוטומטיות).
* ייצוא: Excel (xlsx אמיתי), PDF והדפסה = "יומן שינויים" מקובץ לפי יום עברי (שעה / מי / מה / השינוי עד 3 שדות), רושם `data-history` ב-`pkRegistry.js`, משטח PDF `a5-data-history` -> `page:admin` (נבדק: אנונימי 401, מזכירה 403, הנהלה / מתכנת 200). Excel עד 5,000 שורות (עמודי 500). **הדפסה / PDF: עד 1,500 שורות** (`PRINT_MAX` ב-`historyShared.js`): העימוד מודד פריסה אמיתית לכל גיליון - 3,446 שורות = 187 גיליונות וקיפאון של כמעט דקה (ביקורת עצמאית 2); מעל התקרה נפתח חלון כהה "הרשימה ארוכה מדי להדפסה - צמצמו את הסינון (נדרש עד 1,500 שורות)" ושום דבר לא נטען / נבנה. נמדד: 1,345 שורות = 63 גיליונות, כ-7 שנ' בנייה בדפדפן (+ טעינת 3 עמודי ייצוא; ב-dev מול Neon 9.5 שנ' בגלל RTT).
* **לא נבנה: חיפוש חכם (AI) וסטטיסטיקה** - אין להם קונטקסט / שרת ל-AuditLog (`smart-search` מכיר רק orders / customers / employees / dresses...). הכפתורים לא מוצגים (הכלל: רק עם backend אמיתי).

## גישה והרשאות
* הדף: `app/admin/layout.js` (הנהלה ראשית / מתכנת, אחרת "אין הרשאה"; לא מחובר = מסך כניסה). ה-API החדש: `checkAuth('הנהלה ראשית')` לפני כל שאילתה (401 לכל השאר - נבדק חי עם סשנים שנטבעו: אנונימי, עובד לא פעיל, מזכירה, תופרת, מנהל סניף -> 401; הנהלה ומתכנת -> 200).
* **שורות הנהלה בלבד נשארות הנהלה בלבד** גם בפונקציה עצמה (`visibleTypes` / `buildAuditWhere`): Employee, Shift, EmployeePermissionOverride, DepartmentPermission, PermissionPageGroup, TrustedDevice, ApiKey, Department - לצופה שאינו הנהלה נחתכות מהסינון ומהרשימה (הרשימה זהה ל-`/api/audit`, נבדק בבדיקה). שכר (`hourlyWage*`, `totalCalculated`, `travelExpenses*`, `paymentMethod`) מוסתר לשאינו הנהלה גם בתוך שורות מותרות.
* **סודות לעולם לא יוצאים מהשרת** (`buildChangeList`): סיסמה / PIN / מפתח API / טוקן / ת"ז / חשבון בנק / כרטיס אשראי (כל מפתח ש-`isSensitiveKey` מזהה) - רק "הערך מוסתר"; גוף מייל (`EmailLog.body` - יכול להכיל סיסמה זמנית) ושיחות AI לא נשלחים; טקסט חופשי עובר `cleanText` (מסכה מספרי כרטיס / חשבון, מוחק UUID בתוך טקסט); שדה שערכו UUID נעלם, והחלפת הפניה מוצגת "הוחלף / נקבע / הוסר". נבדק חי: שורות בדיקה עם `PLAINSECRET`, `TEMPSECRET`, ת"ז, חשבון, כרטיס, UUID -> אף אחד לא בתשובה.
* שדות פנימיים / רועשים מוסתרים (id, legacyId, createdAt, updatedAt, מפתחות פונטיים, `themeColor` - העדפות תצוגה, `isWeekdayEvent`...). בשורה שטוחה (CREATE / עדכון בלי לפני-אחרי) "לא" / 0 מוסתרים חוץ מהשדות המשמעותיים (`isDeleted`, `isTaken`... ר' `MEANINGFUL_FALSE`).

## עלות (טבלה ענקית)
`AuditLog` גדלה בכל כתיבה באתר. האינדקסים הקיימים: `(entityType, entityId)` ו-`(employeeId)`; **אין אינדקס על `createdAt`** ואסור DDL. לכן:
1. כל שאילתה בטרנזקציה עם `SET LOCAL statement_timeout = 8s` (`guarded`), בקשה כבדה תחת מגבלת 4 במקביל (`runLimited`), חריגה = 503 "צמצמו את הסינון"; עמוד עד 100 (ייצוא 500), היסט עד 100,000 אחרת 400; חיפוש עד 200 תווים; כל קלט משתמש ב-SQL הוא פרמטר (`$n`), מיון / עמודות מרשימה לבנה.
2. **אין COUNT מלא**: הסך = `SELECT count(*) FROM (SELECT 1 ... LIMIT 100001)` - עד 100,000 שורות תואמות נסרקות; מעל זה מוצג "100,000+" והעימוד נעצר ב-2,000 עמודים. הסך נשמר 30 שניות לכל צירוף סינון (דפדוף לא סופר מחדש).
3. ספירות חלון הסינון (`/counts`) נשלפות **רק כשהחלון נפתח** (דיבאונס 300ms, מטמון 60 שנ'), חסומות לאותה תקרה (דגימה); אם התקרה נפגעת האפשרויות נשארות גלויות בלי מספר (לא מסתירים "אפס" מדומה).
4. `changesJson` מעל 60KB (שיחת AI / גוף מייל) לא נשלף - השורה מסומנת "גדול מדי"; שורות הייצוא כוללות עד 6 שדות לשורה.
5. שמות: עובדים = שאילתת מזהה-ראשי אחת לעמוד; ישויות = אחת לכל סוג שמופיע בעמוד (Order / OrderItem / Payment / PaymentObligation / Customer / DressModel / DressItem / Employee), במקביל, לא חוסמות (כשל = שורה בלי מספר).

### מדידות (TEST, `node --import ./scripts/perf/register.mjs scripts/perf/history-lists-profile.mjs --explain --scale=400000`)
זמני קיר כוללים ~0.75 שנ' RTT לכל שאילתה מהמחשב המקומי מול Neon, לכן ההשוואה האמיתית = מספר השאילתות וזמן הביצוע בשרת ה-DB (EXPLAIN ANALYZE).
| בקשה (TEST, 3,435 שורות) | לפני (`/api/audit?limit=100`) | אחרי (`/api/admin/data-history`, 50) |
|---|---|---|
| שאילתות לעמוד | findMany(100) + שמות עובדים + **count(*) מלא** = 3 | שורות (1) + שמות (1) + ישויות (<=7, במקביל) + count חסום (1, מטמון 30 שנ' - 0 בדפדוף) |
| גודל תשובה | 57 KB | 12 KB |
| ביצוע ב-DB (EXPLAIN) | - | רשימה 2.7 ms, count 1.0 ms (type=Order: 0.6 / 0.4 ms) |
קנה מידה - טבלה זמנית (pg_temp) של **400,000 שורות** עם אותם אינדקסים (ביצוע בשרת, ms): רשימה ללא סינון 283 (סריקה + top-N heapsort, אין אינדקס זמן), סוג=הזמנה 75 (bitmap על האינדקס), פעולה=עדכון 178, עובד=מערכת 99, תקופה 30 יום 87, חיפוש טקסט 380 (סריקה מלאה, ILIKE), מיון לפי עובד 344, מיון לפי היקף 294; count חסום 29-80; קבוצת ספירות 43-96 (חיפוש: 371). כלומר גם פי 100 מהיום כל בקשה מתחת לחצי שנייה - והתקציב (8 שנ') חוסם את הקיצוני.
**המלצה (לא הורצה):** אינדקס `AuditLog(createdAt)` - `prisma/migrations-pending/2026-10-11-auditlog-createdat-index.sql` (CREATE INDEX CONCURRENTLY, אחרי בדיקת זהות ה-DB ואישור הבעלים). הוא יוריד את הרשימה / המיון לפי זמן לאפס-נקודה-משהו מילישניות; בלעדיו הכול עובד אבל כל עמוד קורא את כל השורות התואמות.

## נקודות תיעוד
* `useAdminServerList` קיבל `initialSel` (תואם לאחור; ברירת מחדל של קבוצה צריכה להיות גם בבקשה הראשונה) ושומר `totalCapped`; `A5List` מציג `texts.countSuffix` ("+") ליד המספר בסרגל התוצאות.
* ה-Prisma extension כותב שורת AuditLog לכל כתיבה (כולל כתיבות מהמסך עצמו - אין כתיבות כאלה כאן). אין כתיבת AuditLog ידנית.
* שורות של "העדפות תצוגה של עובד" (`themeColor`) מציפות את היומן (כל החלפת עיצוב) - מוסתרות בפירוט, והשורה נשארת ("אין שדות להצגה").
* לא נבדק: PROD (אין גישה); גודל AuditLog ב-PROD (נתון חסר - המדידה בקנה מידה מכסה עד 400k+).
