## 1. How access control works here

| Layer | Mechanism | Notes |
|---|---|---|
| Middleware | `middleware.js` only forwards `x-pathname`. **No auth.** | By design; everything below is per route. |
| Page shell | `app/layout.js`: when `require_login=true` and no verified cookie it renders `LoginGate` instead of `children`. | `require_login` is `true` on the TEST DB. If it is `false` the whole site is "open mode" (see risk R1). |
| Page gates | `app/employees/layout.js`: `checkPageAccess([0,2])`. `app/dashboard/dresses/layout.js`: `PageGate page:dresses_catalog` (permissions catalog, default closed). | `/dashboard/dresses/new` and `/[id]/print` sit under the same layout. |
| Identity | `auth_token` (raw employee uuid) is trusted **only** together with a matching signed `auth_session` cookie (`getVerifiedAuthCookie`). A hand-typed `auth_token` is anonymous. | Verified: forged cookies are refused. |
| API gates | `checkAuth()` (any verified session, or anybody in open mode), `checkAuth('הנהלה ראשית')` (roles 0, 2), `checkAuth('מתכנת')` (role 2), `getAttendanceViewer()`, `checkAiAccess()` (`feature:ai`), `canOpenPage()`. | `ROLE_LEVELS`: 'מנהל' = [1,2], 'הנהלה ראשית' = [0,2], 'מתכנת' = [2]. |
| Escalation ladder | `canManageRoles` / `roleRank`: 2 > 0 > 1 > rest. | Employee create/edit/password refuse a target or new role above the actor. |
| Page variant | `UI_SCREEN_REGISTRY` + `/api/me/ui-variant/<screen>`: since 2026-10-11 every active employee may switch (owner decision, section 8), only their own record, active state read from the DB. | The new design changes only the component; **it calls the same APIs and the same layouts**, so it inherits all the gates below. |

## 4. Residual risks / owner decisions

* **D1 - dress items: RESOLVED 2026-10-11** (owner: "רק הנהלה - ועל פי ההרשאות הספציפיות שניתן להגדיר"). New configurable action permission `feature:dress_items_manage`, see section 7. Before: any signed-in employee could create, edit and soft-delete `DressItem` rows.
* **R1 - open mode.** If `require_login` is turned off, `checkAuth()` (no role) passes anonymous visitors and `/api/employees?all=true` returns the full HR table to them. Role-gated routes (`הנהלה ראשית`/`מתכנת`) stay closed. Both production organisations must keep `require_login=true` (not verifiable from here: no PROD access).
* **R2 - no brute-force limit** on `set-password` / `reset-password` / `verify-pin` / login (the manager's code is checked server-side with bcrypt but attempts are unlimited). Pre-existing, global; a rate limit belongs in a separate change.
* **R3 - public reads by design:** `GET /api/settings` (secrets masked), `/api/pricelists/categories`, `/api/attachment/[id]` (capability URL: anyone who learns a uuid can fetch error-report screenshots/recordings; uuids are only shown to people who can open those reports), `GET /api/employees` names+ids for the login picker, `/api/queries-by-path` (static explanatory text, no data).
* **R4 - AI smart search (employees context) - RESOLVED 2026-10-11.** `pageContext: 'employees'` used to have no schema and silently searched the Customer table (the legacy employees page showed customers). It now has its own context (`lib/ai/employeesSearch.js`, handler `handleEmployeesSearch` in `app/api/ai/smart-search/route.js`). How it is enforced, in code and not only in the prompt: (1) **Gate** - after `checkAuth()` (401) the route resolves the live session employee and requires head management / programmer (`HEAD_MANAGEMENT_ROLES`), else 403 with a Hebrew message; a deactivated / deleted employee or the open-mode guest is refused (fail closed); `checkAiAccess()` (`feature:ai`, `hide_ai_features`, admin restrictions) still applies on top. (2) **Safe source** - the model writes only a WHERE fragment and it runs against two fixed CTEs (`emp`, `emp_shifts`) that expose only id, employee code, names, department name, active flag, phone1, email, last entry time/day, `inShiftNow`, and shift entry/exit times; password / pinHash / wages / wage snapshots / bank / ID / address / notes / themeColor / roleId / trusted devices / API keys / service accounts (legacyId >= 900000) are not in them, so no SQL can reach them. (3) **Allow-list guard** (`checkEmployeesWhere`) - tokenises the fragment and accepts only allow-listed keywords, pure functions and the quoted safe column names; anything else is refused before the DB: other tables (`"Employee"`, `"Shift"`, pg_catalog...), unknown columns, comments, `;`, `$`, E'' strings, UNION / JOIN / WITH / LIMIT / ORDER BY, FROM over anything but `emp` / `emp_shifts`, functions such as pg_sleep / set_config / generate_series, unbalanced parentheses. (4) **Runtime** - read-only transaction, `statement_timeout` 8 s, fixed outer SELECT list / ORDER BY / LIMIT 200, rows mapped through a key allow-list. Paging tokens stay HMAC-signed per context and are re-checked by the guard. A request that is plainly about passwords / wages / bank / ID / address gets an explanatory message without an LLM call (UX only). Tests: `scripts/test_ai_employees_context.mjs` (114 offline checks) and `scripts/test_ai_employees_live.mjs` (live matrix, real Gemini, TEST DB). **Still open (R4b):** the OTHER contexts (customers / orders / dresses / rentals) still allow sub-selects on any table for a holder of `feature:ai` (e.g. a yes/no probe of `Employee.hourlyWage`); `lib/sqlGuard.js` only blocks credential columns. Closing that needs the same allow-list design per context - not done because it was out of scope and would change behaviour.
* **R4b - AI SQL could read any table - RESOLVED 2026-10-11.** The generic AI endpoints (`/api/ai` chat, `/api/ai/statistics`, `/api/ai/smart-search` for customers / orders / dresses / rentals) get the FULL Prisma schema in the prompt and run the SQL the model writes; `lib/sqlGuard.js` only keeps it read-only and hides credential columns. A holder of `feature:ai` could therefore read - or probe with yes / no sub-selects - `EmailLog.body`, `AuditLog.changesJson`, `SystemSetting`, the permission tables, error reports. New `lib/ai/sqlTablePolicy.js` adds a TABLE allow-list, run right after `assertReadOnlySelect` on every AI query (chat, statistics, smart-search first run / retry / page-reuse / count): **standard** (everyone with `feature:ai`) = business tables (Customer, Order, OrderItem, Payment, PaymentObligation, Refund, DressModel, DressItem, PriceList, PriceRule, DeliveryJoin, ScheduleStageMark, NedarimHok); **management** (roleId 0) + Employee, Shift, Department, AuditLog; **programmer** (roleId 2) + EmailLog, PageVisitLog, ErrorReport(+Reply), Attachment, Notification(+Tag), AuditReport, BackupRun; **never, for anyone**: SystemSetting, ApiKey, TrustedDevice, DepartmentPermission, EmployeePermissionOverride, PermissionPageGroup, AIChatSession, SearchHistory, SavedSearch, QueryLog. Smart-search contexts get an even smaller list (customers = Customer+Order; orders = Order, OrderItem, Customer, DressItem, DressModel, DeliveryJoin, + Payment/PaymentObligation/Refund only when the financial-columns restriction is not hiding money; dresses / rentals similar). Also refused: schema-qualified names (`public.`), `pg_*`, `information_schema`, `current_setting`, `pg_sleep` and similar catalog / DoS functions, `$$` and `E''` strings. Matching is on exact quoted identifiers (Postgres keeps their case; `PriceRule."refund"` is a column, not the Refund table). Evidence before building: `feature:ai` is held today only by head management + programmers (main gemach 4 employees, Neve 9; every department row for roles 1/3/4/6 is `false`), so the live exposure was small, but the permission is configurable and one grant to a regular employee would have opened every table. The 59 real SQL statements the reliability suites recorded (`scratch/ai-reliability-out`, chat / stats / smart-search) use only Customer, Order, OrderItem, DressItem, DressModel and all pass the guard at every tier (0 false blocks). Test: `scripts/test_ai_sql_table_policy.mjs` (schema-sync, tiers, accept / reject matrix, wiring manifest). **Residual:** the table list is not a column list - a standard-tier user with `feature:ai` but without `feature:ai_financial_data` can still ask the chat for amounts in `Payment` / `Order.totalAmount` (the "no financial data" rule for them is prompt text only, as before); no per-row filtering. Both are policy questions for the owner, not regressions.
* **R5 - `agent-login`** compares the secret with `!==` and takes it from the query string (logged by hosting). It is 404 without `AGENT_LOGIN_SECRET`; rotate the secret if it ever appears in a log. Optionally switch to `crypto.timingSafeEqual`.
* **R6 - roles.** `ROLE_LEVELS['מנהל']` = [1,2] excludes head management (roleId 0) - `trusted-device` and a few settings routes lock roleId 0 out (functional, not a leak). `PUT /api/employees/[id]` treats an omitted `isActive` as `true` and an omitted `roleId` as an error, so partial bodies are not safe; the screens always send the full object.
* **R7 - page-level `isActive`.** `app/layout.js` treats any verified cookie as logged in for the shell; a deactivated employee sees an empty shell (no data: every API now refuses them) until the cookie expires.
* **R8 - `GET /api/history`** (page-visit log) was readable by any signed-in employee (documented in `docs/security-visit-log-credentials.md`). **Resolved 2026-10-11** (admin-logs branch): now `checkAuth('הנהלה ראשית')` - its only consumer is `/management/history`, which is head management only; the new `/api/admin/management-history` is gated the same way. `DELETE /api/history` unchanged (manager PIN). See `management-history-notes.md`.
* **R9 - audit scope.** Other entity types (`AIChatSession`, `QueryLog`, `EmailLog`, `ErrorReport*`) are still readable through `/api/audit` by any signed-in employee; no ported screen needs them. **Update 2026-10-11 (section 10, F10):** the `EmailLog` rows turned out to carry the clear-text temporary password of password-reset mails (the audit extension copied the whole mail row, body included) - fixed (masked at write and on read, not searchable). The other listed types remain readable; `AIChatSession` / `QueryLog` rows hold AI questions and answers (customer data), still an owner decision.

### 6.2 Injection / abuse (programmer session, TEST DB)

* Sort keys, filter keys, dates and `ids` are whitelisted/clamped by `parseOrdersListParams` / `parseCustomersListParams`; SQL text is only fixed constants (`ORDER_SNAPSHOT_SQL`, `CUSTOMER_FACTS_SQL`, no placeholders from users; page rows are fetched with Prisma `in: [ids]`). Probes with `; DROP TABLE`, quotes, `OR 1=1`, sub-selects in `sort`/`dir`/`states`/`branches`/`ids`/`search`/`from`/`to`, `__proto__`/`constructor` JSON, array bodies, a 100,000-character search: all answered **200 with ordinary data or empty results**, never a SQL error and no echo.
* Limits: `limit` is capped (100 per page; `export:true` 500), `page` capped, `search` cut to 200 characters. `lib/adminListGuards.js` adds a statement timeout, a request deadline and a concurrency limiter (4) - that layer was still being wired into the routes at audit time (the routes still map every failure to a generic 500, which is safe but gives the user no "narrow the filter" message).
* During the first pass the endpoints returned **500 under load** (Postgres `53200 out of memory` on the small TEST Neon compute: ~25 parallel `count()` queries per counts call and `IN (thousands of ids)` lists). Those were DB resource exhaustion, not input handling; the snapshot-in-memory design that replaced them answers the same probes without errors. Residual: R10.

### 6.3 Server-side HTML -> PDF (`/api/pdf`, `html` + `surface`)

Tested with a hostile document (head session, surface `a5-employees-list`) containing `<link>`, `@import`, CSS `url()`, `@font-face`, `<meta refresh>`, inline and external `<script>`, `fetch()` and `new Image()` in script, `<img>` to `127.0.0.1`, `169.254.169.254`, `file:///C:/Windows/win.ini` and this app's own `/api/employees`, `<iframe>` (http, `file:`, `srcdoc`), `<object>`, `<embed>`, `<video>`, `<audio>`, `<form>`, and a look-alike host `fonts.gstatic.com.evil.test`: a local listener on 127.0.0.1 recorded **0 requests**, the PDF was produced (200). ### 10.3 What was verified and found sound

* **Gates.** Every new route starts its shared `handle()` with the gate (`checkAuth('מתכנת')` for the e-mail log, `checkAuth('הנהלה ראשית')` for the two history lists) before reading a parameter or touching the DB; only `GET` and `POST` exist; no write call; no raw error text in a response (asserted by the manifest; generic 500 "Failed to ..."). A deactivated head-management or secretary session is 401 on every API (F3 cache). Role matrix above: 0 deviations.
* **SQL hygiene.** The three builders (`lib/adminEmailLogs.js`, `lib/adminAuditList.js`, `lib/adminVisitList.js`) only bind user values as `$n` arguments (search is wrapped by `likePattern` / `likeEscape`); every interpolation into SQL text is a code constant: allow-listed `ORDER BY` expressions (an unknown `sort` falls back to the default, `dir` is `asc` / `desc`), clamped integers for `LIMIT` / `OFFSET` (page 1..100000, limit 1..100, export 500, offset <= 100,000 -> 400), id lists capped (60 / 20), enum filters through `pickKnown`, dates through the `YYYY-MM-DD` shape, `SET LOCAL statement_timeout` built from a clamped integer. Asserted with hostile input in the manifest (`'; DROP TABLE`, `UNION SELECT`, `${7*7}` never appear in SQL text). Live: 25 hostile strings on `search` and 7 on every other parameter of all 6 endpoints (GET and POST; 100,000 characters, NUL byte, SQL, `__proto__`, template text, `pg_sleep`), 12 JSON edge bodies per endpoint (`__proto__`, `constructor`, arrays, `null`, non-JSON, negative / huge page and limit, `export:"true"` with limit 501, objects where strings are expected): **no 5xx, no SQL / stack text, hostile text is only data**; sort / filter probes return the same rows as the default request.
* **Cost caps.** Page <= 100 (export 500, <= 5,000 rows from the UI), offset <= 100,000, search <= 200 characters, `statement_timeout` 8 s per statement, request deadline 20 s, at most 4 heavy requests per server instance (503 "busy"), counts capped at 100,000 scanned rows with a 30 s cache (list) / 60 s cache (filter options) and in-flight de-duplication, filter-option counts fetched only when the filter popup is open (debounce 300 ms), search debounce 400 ms. A burst of 12 parallel list requests is answered 200 / 503 (in the final run 7 of 12 were refused as busy), never 500.
* **Data in rows.** No password hash, PIN, API key, ID number, card number or UUID reference is returned by any new list (UUID-valued fields become "הוחלף / נקבע / הוסר", text goes through `cleanText`); row keys contain no `pass` / `pin` / `hash` / `secret` / `token` / `body` names; the only UUIDs present are row ids and the link targets of the entity shortcut (`/customers/<id>`, the same ids the pages already use; an employee id alone is not a credential - a forged `auth_token` without the signed `auth_session` is anonymous). Wage fields are filtered by `canSeeWages` in the pure function (and `HEAD_ONLY_AUDIT_ENTITIES` is enforced inside it too), so a future non-head caller would get none; the routes themselves are head-only. The visit log shows redacted URLs and bodies only (the seeded token in the URL and the password in the request body never came back; the body search is refused for secret-looking bodies).
* **Password-reset mails (owner question).** The temporary password reaches the system in three places: `EmailLog.body`, its `AuditLog` twin (**F10, fixed**), and the mail itself. After the fix **no new endpoint, export (xlsx / PDF / print sheet) or search returns or matches it** for any role: the e-mail log API selects `body` only through `CASE WHEN subject ~ <password-reset regex> THEN NULL ELSE left(body,300)`, never in export mode, and its search skips those bodies (the subject regex equals the catalog subject, asserted); data history masks `body` and cannot search rows that carry it; `/api/audit` masks on read. The only place that still shows it is the **old** programmer-only API `GET /api/email-logs` (unchanged; returns whole rows) and the DB itself.
* **Delete flow (`DELETE /api/history`).** Brute force: no limiter (R2, unchanged), now reachable only with a head-management / programmer session; replay: the code is a password sent per request, there is no token to replay and repeating the same request deletes nothing more (verified 200); CSRF: `SameSite=Lax` + JSON body (preflight) - a cross-origin request without the cookie is 401 (verified, row untouched); who may call: head management + programmer sessions, and the code itself must belong to an active manager (role 1, 0 or 2); modes: `ids` (a list), `olderThanDays` (positive integer else 400; verified `deletedCount: 0` for 36500), `deleteAll` - every mode only after the code check, nothing is deleted on a wrong / missing code (verified); `PageVisitLog` is outside the audit extension, so **deletions are not audited** (residual, 10.5).
* **Print surfaces.** The four new surfaces map to `page:admin` (not configurable); anonymous / deactivated 401, secretary / seamstress / branch manager 403, head and programmer 200 `application/pdf`; unknown / `__proto__` / `constructor` / array / numeric surface 400. The sheets contain no body, subject, sender (e-mail log) and no UUIDs or secrets (`pkSpecsAdmin.js` / `pkSpecsHistory.js`, every dynamic text through `escH`; the e-mail log sheet prints recipient, type, status and the failure reason only). The list Excel / PDF fallback (`exportList.js`) escapes HTML and writes string cells, so a recipient like `=cmd|...` cannot become a formula.
* **Variant registry / page shell.** The four new `UI_SCREEN_REGISTRY` entries are frozen, `selfSwitch: true`, both versions exist; no gate file (`lib/auth.js`, `authTokens.js`, `roles.js`, `permissions.js`) reads the variant; the Switch components contain no access logic; the kit / shell refactor (`A5ListPage`, the four earlier lists now rendering through it) keeps every handler and the `isHead` button gate unchanged.
