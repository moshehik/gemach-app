# חוזה פונקציונלי — ארכיטיפ "כרטיס פרט" (A2), פיילוט: כרטיס לקוח `/customers/[id]`

> **מה זה:** רשימה ממוספרת (CC-n) של כל מה שהעמוד עושה היום, כפי שחולץ מהקוד בענף `redesign/v3-master-plan` (בסיס: `8dbd3c7`), 2026-09-24.
> **מה זה לא:** לא מפרט עיצוב ולא העתקת מלל. בכוונה **אין כאן markup, CSS או ניסוחים ישנים** — כל פריט מתאר *פונקציה*, והמלל בעמוד החדש נכתב מחדש (C-1.7 / R10).
> **מקורות שנקראו:** `app/customers/[id]/page.js`, `app/customers/layout.js`, `components/customers/modern/{ModernCustomerCard,ModernCustomerDetailsTab,ModernCustomerOrdersTab,ModernCustomerPaymentsTab,ModernCustomerRefundsTab,ModernCustomerHistoryTab,ModernSendEmailModal,customerDialogs}.js`, `components/orders/modern/mocAuth.js`, `app/api/customers/[id]/route.js`, `lib/permissionsMetadata.js` (`feature:customer_email_approval`). עזר: `contracts/customers-id.md` (חוזה ישן, נכתב לפני ההמרה ל-v3 kit — בחלקו מיושן; היכן שיש סתירה, הקוד הנוכחי קובע).
> **האב-טיפוס:** `archetype-detail-card.html`. מיפוי CC → אזור באב-טיפוס: `README.md`.

סימון עמודת "סוג": **D** נתון מוצג · **I** קלט · **A** פעולה/כפתור · **G** שער הרשאה · **S** מצב (טעינה/ריק/שגיאה) · **N** קריאת רשת · **O** תלוי-הגדרה/ארגון · **B** התנהגות.

## 9. פערים ושאלות שנמצאו תוך כדי (לא מתוקנים — תיעוד בלבד)
1. **חזרה עם שינויים (CC-24):** היום נזרקים בשקט. ארכיטיפ A2 (חוקה §ו) דורש Confirm תלת-דרכי. זו תוספת *התנהגות* (שמירה/השלכה/המשך) — האב-טיפוס מציג אותה; לאישור המשתמש. (PROTOTYPE-QUESTIONS Q3)
2. **שלושה כפתורי שמירה** (כותרת, V בכרטיס, תחתית טופס) ושני מודלי עריכה (מצב עריכה מקומי + שמירה כללית). A2 = CTA אחד ברייל. האב-טיפוס מציג CTA אחד ברייל + כפתור שמירה בתחתית הטופס (CC-39, בקשת עובדת) שקורא לאותו מסלול. (Q2)
3. **כשל טעינה = מסך ריק** (CC-7). האב-טיפוס מציג מצב שגיאה + "לנסות שוב" — שינוי UI בלבד (אותה קריאה). (Q5)
4. **`persistToBell:true`** בקוד הנוכחי (CC-64) סותר את D-4. האב-טיפוס מציג NoticeBar זמני בלבד.
5. **ספירה כפולה אפשרית בחוב** (אבחון 03 §6.2): זיכוי שבוצע יוצר גם תשלום שלילי, והיתרה מחסירה שוב את הזיכוי. לא אומת. האב-טיפוס מציג את הנוסחה הקיימת כפי שהיא; לא לשכפל לנוסחה חדשה לפני הכרעה. (Q6)
6. **היסטוריה = לקוח בלבד** (CC-59). פיד מאוחד (הזמנות/תשלומים/זיכויים של הלקוח) דורש פרמטר קריאה תוספתי בשרת (אבחון 03, HISTORY-DESIGN §3.1) — מחוץ לתחום הקוסמטי. האב-טיפוס מציג פיד לקוח עם תווית ברורה "שינויים בפרטי הלקוח", ומסמן בהערה את האפשרות העתידית. (Q7)
7. **כלל ה-ID:** נפילה למזהה UUID בכותרת כשאין `legacyId` מפרה את כלל התצוגה (AGENTS.md). האב-טיפוס מציג "ללא מספר" במקרה כזה. (Q8)
8. **חוזה ישן מיושן:** `contracts/customers-id.md` מתאר את המבנה לפני ההמרה ל-kit (עמודות טבלה, מלל). שינויים עיקריים בקוד מאז: טבלאות הפכו לשורות מורחבות, alerts לחלוניות.

## 10. UI בלבד מול מה שהעיצוב צריך מהנתונים
**UI בלבד (אפשר לבנות בלי לגעת בשרת — כל הנתונים כבר נטענים):**
- רייל "במבט אחד": מספר הזמנות, יתרה (אותה נוסחה של CC-49), הזמנה קרובה (מתוך `customer.orders`), סטטוס חסימה.
- רשימת שינויים עם ביטול/שחזור פר-שורה לשדות שטוחים של הלקוח (השוואת `customer` מול `originalCustomer` שדה-שדה) — שכבת מצב-ותצוגה, אותו payload (חוקה §ז; המנוע עצמו ממתין ל-D-7).
- Confirm תלת-דרכי ביציאה (מקומי, לפני הניווט) — אבל זו התנהגות חדשה → דורש אישור.
- מצב שגיאת טעינה עם "לנסות שוב" (אותן קריאות).
- החלפת `alert` בשגיאה inline/toast; NoticeBar "נשמר" (קיים).
- פיד היסטוריה מקובץ לפי יום עם משפטים אנושיים — מתאם קריאה בלבד (`HistoryFeed` + adapter קיימים), על אותה תשובת `/api/audit`.

**צריך נתונים/שרת (מוכח):**
- פיד מאוחד של כל פעולות הלקוח (הזמנות, תשלומים, זיכויים) — `api/audit` מחזיר רק `entityType=Customer` לפי מזהה יחיד; איחוד מלא דורש פרמטר קריאה תוספתי (`customerId=`) או N קריאות (אבחון 03 שורה 117). **לא נדרש לפיילוט.**
- אישור נוסחת החוב (שאלה 5 לעיל) — הכרעה עסקית, לא נתון חסר.
- אין צורך בשדה חדש כלשהו כדי להציג את האב-טיפוס.
