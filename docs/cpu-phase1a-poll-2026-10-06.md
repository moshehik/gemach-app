# שלב 1A - בדיקות רקע זולות יותר (6.10.2026)

ענף: `perf/phase1a-poll-2026-10-06` (מבוסס על origin/main 491f71bb + הענף `perf/idle-tab-guard-2026-10-06`). שום דבר לא נדחף ולא נפרס.
המטרה: להוריד את עלות ה-CPU (Vercel Fluid Active CPU) של בדיקות הרקע של "לא נקראו" - פעמון ההתראות וכפתור דיווח התקלות.

## מה היה
כל טאב גלוי דגם **שתי** בקשות נפרדות כל 120 שנ': `/api/error-report?light=1` ו-`/api/notifications?light=1`. כל בקשה = invocation עם אימות,
`employee.findUnique`, שתי שאילתות הרשאה ו-`findMany` (בדיווחים: כל הדיווחים בארגון אצל מתכנת, רק כדי לספור). בנוסף הפעמון דגם בכל ניווט.

## מה השתנה

### שרת
- **`GET /api/poll`** (`app/api/poll/route.js`) - בקשה אחת שמחזירה את שני המונים:
  `{ success, errorReports: { unread, isProgrammer, isManager } | null, notifications: { unread } | null }`.
  חלק שנכשל מחזיר `null` והשני ממשיך. 401 בלי משתמש חתום, 404 לעובד שנמחק (כמו `/api/error-report`).
- **אותה סמנטיקה בדיוק** (`lib/pollCounts.js`): מתכנת (roleId 2) סופר את כל הדיווחים, כל השאר רק את שלו; "לא נקרא" = לא בארכיון ו-
  (מתכנת: `!isReadByProgrammer`, אחר: `!isReadByUser`) - זהה ל-`countUnread` ב-`erModel.js`. הספירה נעשית ב-`count()` במקום למשוך כל שורה
  (כל השדות לא-nullable בסכימה, ולכן `status != 'ARCHIVED'` זהה ל-JS; נעילת הסכימה נבדקת בטסט). `isManager` = `hasPermission(employee, 'feature:error_reports')`.
  ההתראות: אותו `where` / `orderBy` / `take: 150` ואותו חישוב isRead/isArchived (כלליות לפי readBy/archivedBy) כמו `?light=1` הישן.
- **אימות זול:** עוגיית `auth_token` מאומתת מול הטוקן החתום (HMAC, בלי DB) והתפקיד נלקח מ-`readVerifiedSession` (טוקן טרי, עד 15 דקות - אותו מודל
  אמון של `checkAuth`). אין `employee.findUnique` בדגימה; רק כשאין טוקן טרי (עוגייה ישנה) שאילתה אחת, ורק כשהמטמון ריק. תפקיד שהשתנה בטוקן לא נלקח מהמטמון.
  `isManager` נשמר במטמון 30 שנ' (משפיע רק על הצגת כפתור "דיווח חדש"; `POST /api/error-report` בודק הרשאה שוב בשרת). לא נחלשה אף בדיקה: המונה
  מוחזר רק לעובד המחובר עצמו וסופר רק את מה שהוא רשאי לראות.
- **מטמון לכל עובד** (`lib/pollCache.js`, אותו דפוס כמו `settingsCache.js`): 30 שנ' לכל אחד משני המונים. מדגם "פגיעה" = אפס שאילתות.
- **הגבלת קצב לכל עובד:** דלי אסימונים (פרץ של 3, אחר כך אסימון לכל 20 שנ'). מעבר לכך - מוגש ערך המטמון עם הכותרת `X-Poll-Limited: 1`, בלי שגיאה
  (ואם אין מטמון בכלל - מחשבים). `?fresh=1` עוקף את המטמון (לא את ההגבלה).
- `Cache-Control: no-store` בכוונה (ר' "הערות" למטה).
- **הנתיבים הישנים לא שונו** (`/api/error-report?light=1`, `/api/notifications?light=1`): עותקי JS ישנים בדפדפנים + `LegacyErrorReportButton.js` הקפוא שדוגם בעצמו.

### לקוח
- `lib/pollClient.js` - דוגם **אחד לטאב** (סינגלטון), עם מנויים. טיימר אחד דרך `onActiveInterval` של `lib/idleGuard.js`: נעצר בטאב מוסתר ובטאב שנשכח פתוח
  (30 דקות בלי פעילות), ובחזרה (גלוי / תזוזה) בקשה מיידית אחת. **קצב: 300 שנ' (היה 120).** הכתובת היא `/api/poll?light=1` (ה-`light=1` בכוונה:
  `app/layout.js` לא רושם בקשות כאלה ב-PageVisitLog, ושער ה-fetch של idleGuard מחזיר מקומית "מושהה" בטאב לא פעיל).
- **דה-דופליקציה:** פעמון + כפתור שעולים יחד = בקשה אחת (בקשה בדרך משותפת; תוצאה טרייה מ-5 שנ' משמשת שוב). מנוי מאוחר מקבל מיד את התוצאה האחרונה.
- **רענון מיידי אחרי פעולה של המשתמש עצמו** (`pollAfterAction()`, דחוי שנייה אחת כך שרצף פעולות = בקשה אחת, עם `?fresh=1`): סימון כנקרא / ארכיון / "סמן הכל" /
  "נקה" בפעמונים, סגירת חלון דיווח התקלות (כיסוי לדיווח חדש, תגובה, סימון), וכל פעולה רלוונטית בדף `/messages`. פתיחת הפעמון: רענון אם עברו 30 שנ'. ניווט: רענון אם עברה דקה.
- 401 (עמדת לקוחות, דפי הדפסה): הטיימר נעצר ו-`authFailed`; ניווט מנסה שוב.
- `lib/usePoll.js` - hook `usePollSnapshot()`. הרכיבים שהוחלפו: `ErrorReportButton.js` (הגרסה החדשה), `NotificationBell.js`, `menu/MenuBell.js` (+ שלוש קריאות ב-`app/messages/page.js`).
- **לא נערך:** `LegacyErrorReportButton.js` (קפוא) ממשיך לדגום `/api/error-report?light=1` כל 120 שנ'; שער ה-idle מחזיר לו "מושהה" כשהטאב לא פעיל.
  מסך "ישן" הוא ברירת המחדל לכל התפקידים חוץ ממתכנת, ולכן אצלם החיסכון בצד דיווח התקלות יתקבל רק אחרי שיופסק השימוש בעותק הישן; הפעמון כבר חוסך.

## חיסכון צפוי (הערכה, לא מדידה)
- לפני: ~60 בקשות לשעה לטאב פעיל (30 + 30), כל אחת ~4 שאילתות ואימות => כ-1.2 שנ' CPU לטאב-שעה.
- אחרי: 12 בקשות לשעה (+ כמה ניווטים), רובן פגיעות במטמון של 30 שנ' או עם 1-3 שאילתות (`count` + הרשאה + התראות), בלי `findUnique` של העובד => כ-0.3 שנ' CPU לטאב-שעה.
- טאב גלוי שנשכח פתוח: נעצר אחרי 30 דקות (מ-idleGuard), כמו קודם.
- אימות מדויק: לוגי Vercel Functions לנתיב `/api/poll` מול `/api/notifications` ו-`/api/error-report` (עם `light=1`), לפני ואחרי הפריסה.

## הערות
- **מטמון לכל אינסטנס בלבד.** ב-Vercel כל נתיב API הוא פונקציה נפרדת, ולכן "ביטול מטמון" מנתיב אחר (`POST /api/notifications/read`) לא מגיע לאינסטנס של `/api/poll`
  (אותה מגבלה קיימת ב-`settingsCache`). לכן **לא חוויטו כתיבות** (הקוד של הכתיבות לא נגוע) והנכונות אחרי פעולה עצמית נשענת על `?fresh=1` מהלקוח; שינויים של
  אחרים (הודעה חדשה, תגובת סוכן שנכתבת ישירות ל-DB) מגיעים תוך TTL (30 שנ') + מחזור הדגימה. ה-helpers `invalidateErrorReportCounts` / `invalidateNotificationCounts` קיימים
  (בדוקים) לשימוש אינסטנס-מקומי.
- `max-age=30` לא הוגדר (הסיכון שתועד ב-`docs/idle-tab-guard-2026-10-06.md`: מונה ישן מיד אחרי "סמן כנקרא").
- ה-`/api/poll` יושב מאחורי אותו `middleware` כמו שאר ה-API (אין עליו שום ריצת middleware).

## איך בודקים בדפדפן
1. התחברו, DevTools -> Network, סננו `poll`. אמורה להיות בקשה `/api/poll?light=1` אחת בעת הטעינה (גם כשיש פעמון וגם כפתור דיווח), ואחריה אחת כל 5 דקות. אין `/api/notifications?light=1` ואין `/api/error-report?light=1`
   (חוץ ממסך הדיווח "הישן", שממשיך לדגום בעצמו).
2. עברו לטאב אחר 10 דקות: אין בקשות. חזרה: בקשה אחת מיידית.
3. השאירו גלוי בלי לגעת 31 דקות: הבקשות נפסקות; תזוזת עכבר = בקשה אחת.
4. סמנו הודעה כנקראה בפעמון: כעבור כשנייה בקשה `/api/poll?light=1&fresh=1` אחת, והנקודה האדומה נשארת נכונה.
5. ניווט בין דפים: לא יותר מבקשה אחת לדקה.
6. תגובת השרת: כותרת `Cache-Control: no-store`; ובפרץ מהיר (כמה רענונים תוך 20 שנ') `X-Poll-Limited: 1` בלי שגיאה.
