# תכנון פיצ'ר משלוחים — פערים מול המצב הקיים (2026-09-16)

מסמך זה ממפה את **המצב הקיים** של פיצ'ר המשלוחים מול הדרישה המקורית, ומתכנן את מימוש
החלקים החסרים, כולל מיקום מדויק של כל קובץ שייווצר/ישתנה. נכתב לפני תחילת עבודה —
לעדכן/לסמן משימות שהושלמו תוך כדי מימוש בפועל.

אין מודל `Delivery` נפרד ב-DB. כל הלוגיקה הקיימת בנויה על `Order.isDelivery` /
`Order.deliveryDirection` / `Order.deliveryCity` (ראה `prisma/schema.prisma`). התכנון
להלן **ממשיך את אותה גישה** ולא מציע מודל Delivery חדש, אלא אם יתגלה צורך אמיתי.

**עדכון סטטוס:** מומש **§A** (2026-09-16, ר' `CLAUDE.md` לפירוט המלא). כל שאר הסעיפים
(§B/§C/§D/§E) עדיין בתכנון בלבד, לא מומשו.

**גילוי חשוב מ-§A שמבטל דאגה שהייתה בתכנון המקורי:** ה"החלטה הפתוחה" שסומנה למטה
(סעיף א.4, "מתי בדיוק משלוח 'נוצר'") פחות קריטית ממה שנראה מלכתחילה - `applyDeliveryCharge`
(`lib/pricingEngine.js:613-659`) כבר רץ בכל שמירה (יצירה ו-**עדכון** כאחד) ולא יוצר כפל
חיוב (בודק `exists` לפי תיאור "משלוח" לפני יצירה), ו-`recalculateOrderObligations`
שרץ תמיד לפניו כבר מוחק כל התחייבות משלוח שאינה עקבית עם מצב ההזמנה הנוכחי. כלומר: כיבוי
משלוח בהזמנה קיימת כבר מבטל את החיוב אוטומטית בשמירה הבאה, בלי צורך בשינוי נוסף. ה"יצירה
בשמירה ולא באישור תשלום בפועל" עדיין נכונה כתיאור המצב, אבל אינה משאירה חיובים יתומים.

## א. טופס משלוח בהזמנה קיימת

**בעיה:** הרכיב קיים רק ב-`app/orders/new/page.js`. בעריכת הזמנה קיימת
(`app/orders/[id]/page.js` / `components/orders/modern/ModernOrderCard.js`) אין דרך
להוסיף/לערוך משלוח אחרי היצירה.

**תכנון:**
1. לחלץ את בלוק ה-UI של המשלוח מ-`app/orders/new/page.js` (שורות ~1950-2040) לקומפוננטה
   משותפת, למשל `components/orders/DeliverySection.js` — טוגל, כיוון, עיר, כתובת
   חלופית, צ'קבוקס "יום לפני". מקבלת props של ערך נוכחי + onChange, כדי שגם וויזארד
   ההזמנה החדשה וגם עריכת הזמנה קיימת ישתמשו באותו רכיב (למנוע כפילות/סחיפה).
2. לשלב את הקומפוננטה ב-`ModernOrderCard.js` (איפה שמוצגת שאר האינפורמציה על ההזמנה) —
   צריך להחליט אם מוצגת תמיד או רק דרך פעולת "ערוך".
3. ב-API: `app/api/orders/[id]/route.js` כבר קורא ל-`applyDeliveryCharge` (שורה 811) בעת
   עדכון הזמנה — צריך לוודא שהשדות `isDelivery`/`deliveryDirection`/`deliveryCity`
   מתקבלים ונשמרים גם בעדכון (לא רק ביצירה), ושמעבר ממשלוח ל"אין משלוח" מבטל את
   ה-`PaymentObligation` הרלוונטי בלי להשאיר חיוב יתום.
4. **החלטה פתוחה:** הדרישה המקורית אומרת "ברגע שיש אישור תשלום של משלוח, אוטומטית נוסף
   משלוח למערכת" — כרגע ה-`isDelivery` נשמר מיד עם שמירת ההזמנה, לא בהמתנה לאישור
   תשלום, כך שהמשלוח כבר "קיים" (מופיע בלשונית משלוחים) גם לפני שהתשלום אושר בפועל.
   צריך להחליט: האם זה בסדר (משלוח = כוונה, לא תלוי תשלום), או שנדרש שינוי בפועל כך
   שהמשלוח יופיע בלשונית רק לאחר ש-`PaymentObligation` המשויך שולם.

## ב. סטטיסטיקת משלוחים לפי עיר — ✅ מומש 2026-09-16

`app/admin/ai/page.js`/`app/admin/statistics/page.js` (איפה שמוצגות "הסטטיסטיקות של ה-AI"

CLAUDE.md). במקום זאת נבחרה החלופה הקלה שהמסמך הזה כבר הציע: פילוח ("ירושלים: 3 · קרית
ספר: 2 · ביתר: 5") מוצג ישירות ב-`app/deliveries/page.js`, מעל טבלת המשלוחים, ומחושב
לגמרי בצד הלקוח (`useMemo`) מהנתונים שכבר נטענו - **בלי endpoint/query חדש בשרת**.
- `lib/deliveries.js` - נוסף שדה `city` נפרד לכל שורה (בעבר היה רק `address` המשולב

- `app/deliveries/page.js` - `cityBreakdown` (`useMemo`): ביום בודד סופר לפי `filteredRows`
  (כולל חיפוש חופשי, עקבי עם הטבלה הראשית); בתצוגת טווח סופר על כל הימים שנטענו

  לא מסננת לפי חיפוש).

## ג/ד/ה. מומש בפועל (2026-09-16) — הדפסה/שליחה למשלוחן + הדפסת שקית

**סטייה מהתכנון המקורי (לטובה):** לא נוצר `courier-export` route נפרד. גילוי בזמן המימוש -
`GET /api/deliveries?date=` הקיים כבר מחזיר בדיוק את השדות הדרושים (שם, כתובת, 2 טלפונים,
כיוון) לכל יום בודד, ו-`app/deliveries/page.js` כבר קורא לו בלולאה על טווח ימים (§18, טבלת
טווח). כל §C/§D/§E נבנו כשימוש חוזר באותו endpoint + לוגיקת קיבוץ/כותרות משותפת חדשה, במקום
לשכפל את חישוב חלונות ההלוך/חזור ב-route ייעודי.

**קבצים חדשים:**
- `lib/deliveries.js` — `getDeliveriesForDate(date)`, קוד שרת בלבד (מייבא Prisma). זו בדיוק
  הלוגיקה שהייתה בעבר בתוך `app/api/deliveries/route.js` (GET) - הועברה לכאן כדי ש-
  `courier-email` route תוכל להשתמש באותה שאילתה בלי POST פנימי ל-API עצמו. הוספתי
  `customerFirstName`/`customerLastName` נפרדים לתגובה (נדרש לתוויות השקית, §E).
- `lib/deliveryCourier.js` — לוגיקה טהורה בלי תלות ב-Prisma (בטוחה גם ל-client component):
  `buildCourierGroupTitle` (בונה את הכותרת), `groupDeliveryRowsForCourier` (מקבצת שורות
  ממספר ימי-שיגור לחתכי כיוון+תאריך-אירוע, כל חתך = טבלה/סעיף נפרד), `isoRangeToDates`,
  `dateToIso`.
- `lib/hebrewDate.js` — נוספה `getHebrewWeekdayFullName` (שם יום מלא, "יום רביעי" ולא "יום ד'"
  כמו `getHebrewWeekdayLabel` הקיימת - נדרש בדיוק לניסוח שסופק).
- `app/print/delivery-courier/page.js` (§C) — עמוד הדפסה, query params `direction`
  (out/return/both) + `from`/`to`. שולף מ-`/api/deliveries` per-day בצד הלקוח (כמו
  `app/deliveries/page.js`), מקבץ, ומדפיס טבלה+כותרת נפרדת לכל קבוצה.
- `app/api/deliveries/courier-email/route.js` (§D) — POST, אימות `checkAuth` + בדיקת
  `enable_deliveries==='true'` וקיום `courier_email`, שולח דרך `sendSystemEmail`
  (`lib/mailer.js`, אותה תשתית Apps Script כמו כל מייל אחר).
- `lib/emailTemplates.js` — נוספה `renderCourierDeliveryEmailHtml({ groups, gmachName })`,
  משתמשת ב-`.files-table` הקיים (טבלת נתונים גנרית, לא ה-`meta-table` הדו-טורי).
- `app/print/delivery-bag/page.js` (§E) — עמוד הדפסה, query param `date` יחיד. מסנן
  `directions.includes('out')` בלבד. `@page { size: A4 landscape }` מקומי לעמוד הזה בלבד,
  דף נפרד לכל הזמנה (`page-break-after: always`).
- `scripts/seed_courier_settings.js` — **לא הורץ**. יוצר את שורות ה-`SystemSetting`
  `courier_email`/`courier_name` (עדיין לא קיימות ב-DB בפועל) - ריק לשני הארגונים, לפי הנוהל
  הקבוע ב-CLAUDE.md להגדרות חדשות. יש להריץ ידנית ואז למלא כתובת אמת בהגדרות הניהול.
- `lib/settingsMetadata.js` — נוספו שמות/הסברים ל-`courier_email`/`courier_name`, וגם
  ל-4 מפתחות קיימים שהיו בשימוש בקוד (`enable_deliveries`,`delivery_days_before/after`,
  `delivery_price`) אבל היו חסרים ב-metadata (לא הופיעו בכלי ה-AI settings-guide).

**UI:** כפתור "הדפסת משלוחים" חדש ב-`app/deliveries/page.js` (ליד `ExportButtons`) פותח מודל
עם 3 טאבים (הדפסה למשלוחן / שליחה במייל / הדפסת נתונים לשקית), עצמאי לגמרי מהבחירה הנוכחית
בטבלת העמוד (תאריך/כיוון/טווח נבחרים מחדש בתוך המודל, לפי הדרישה המקורית).
