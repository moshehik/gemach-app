## What this is

A Next.js (App Router) management system for a "gemach" (גמ"ח) — a free-loan society that lends out wedding/event dresses. It tracks customers, employees, dress inventory (models + physical items), rental orders, payments/refunds, price lists, work shifts, and internal messaging. UI and data are Hebrew, RTL.

**One codebase, two production organisations** — "same code, different database"; there is no second copy of the code. Every push to `main` of `moshehik/gemach-app` builds both Vercel projects:

| | org1 — the main gemach (הגמ"ח הראשי) | org2 — נווה יעקב |
|---|---|---|
| Live site | `gemach-app-uyh4-beryl.vercel.app` (Vercel project `gemach-app-uyh4`) | `gmach-neve-yaakov.vercel.app` (Vercel project `gmach-neve-yaakov`) |
| Database | Neon project `gemach-main-prod`, us-east-1 (functions region `iad1`) | Neon project `gemach-dresses-2`, eu-central-1 (functions region `fra1`) |
| Scripts reach it via | `.env` `PROD_DATABASE_URL`/`DATABASE_URL`, GitHub secret `DATABASE_URL`, `--org=1` | `DATABASE_URL_ORG2`/`PROD_DATABASE_URL_ORG2`, or `PROD_DATABASE_URL` inside `scratch/new_gemach_db.env` (that name means org2 there), GitHub secret `DATABASE_URL_ORG2`, `--org=2` |

Verified 2026-09-20 ([docs/vercel-resource-audit-2026-09-20.md](docs/vercel-resource-audit-2026-09-20.md)); DB hosts have moved before, so re-read the env file before trusting one. Code fixes reach both orgs automatically; business rules differ only through `SystemSetting` rows in each org's own DB (see Standing rules).

## Commands

Run from `gemach-app/` (the app root; the parent folder holds unrelated legacy Access-migration files and is not part of the app).

```bash
npm run dev               # next dev --webpack (http://localhost:3000)
npm run build             # prisma generate && next build --webpack
npm run start
npm run lint              # eslint
npm run backup:prod       # manual full SQL dump, org1 (+ org2 if configured) - costs Neon egress, see BACKUPS.md
npm run cleanup:logs      # delete PageVisitLog/QueryLog rows older than 90 days
npm run setup:backup      # (re)provision the local Scheduled Tasks; the backup task is registered DISABLED
npm run generate:offline  # generate @prisma/local-client for offline mode (needs SQLITE_URL)
npm run offline:db-push   # create the local SQLite tables for offline mode
```

- Node `^22.17.0 || >=24` (`package.json` engines); Next 16.2, React 19.2, Prisma 5.22 — read AGENTS.md about Next 16 before writing Next code.
- **No automated test suite** (no Jest/Vitest). Verify with one-off scripts, the dev server, `npx eslint <files>`, and the read-only AI harness [scripts/ai-reliability/README.md](scripts/ai-reliability/README.md). `eslint.config.mjs` ignores root `*.js`, `scripts/**`, `scratch/**` and `.claude/worktrees/**`.
- The repo root is cluttered with historical one-off scripts (`check_*.js`, `fix_*.js`, `test_*.js`, `migrate_*.js`, `scratch_*.js`, …). They are not app runtime and not a source of truth for current behaviour; put new throwaway work in `scratch/` (gitignored).
- The pre-commit hook lives in the shared `.git/hooks`, so it runs in every worktree: it executes `scripts/update_build_time.js`, which bumps the `package.json` version and `app/version.json` on every commit — so every worktree (even a sparse one) must contain `scripts/update_build_time.js`, `package.json` and `app/version.json`.
- Next 16 allows one `next dev` per directory. If a route that exists on disk answers with Next's 404 page, delete `.next` and restart. Edits to `app/lib/prisma.js` need a full dev-server restart (the extended client is cached on `globalThis`).

## Architecture

### Database: prod/test switch, web backup mode, offline mode (dual/offline database mode)
[app/lib/prisma.js](app/lib/prisma.js) exports a `Proxy` over a prod and a test client. App code always imports it from `@/app/lib/prisma` — never `new PrismaClient()` inside the app (standalone scripts use a raw client on purpose, e.g. `scripts/insert_audit_report.js`).
- Prod client = `PROD_DATABASE_URL || DATABASE_URL`; test client = `TEST_DATABASE_URL` (only when set).
- **Local dev switch:** under `next dev` the proxy uses the test client when the mode is `test`. The mode is read once per process from `.active-db` in the process CWD (tracked in git with value `prod`) and flipped by the dev banner (`app/components/DevEnvBanner.js` → `POST /api/dev/switch-env`, development only), which rewrites the file and the in-memory `globalForPrisma.activeDbMode`. It is process-global — flipping it redirects every session using that dev server. Each worktree has its own `.active-db`.
- **Production switch ("web backup mode"):** `SystemSetting` `web_backup_mode` in the PROD DB (settings → מסד נתונים, `WebBackupModeToggle` → `/api/admin/db-mode`, head management only) points every instance at `TEST_DATABASE_URL` (polled every 5 s). On Vercel `TEST_DATABASE_URL` is each org's separate backup Neon project (created 2026-09-20). The flag lives in the PROD DB, so it cannot be flipped while PROD is unreachable.
- **Offline mode:** `IS_OFFLINE_MODE=true` swaps in a generated `@prisma/local-client` (SQLite, schema [prisma/schema.local.prisma](prisma/schema.local.prisma); `prisma/schema-sqlite.prisma` is an unrelated, stale file despite the similar name). It is not generated by `npm install`/build (Vercel would then need `SQLITE_URL`): run `npm run generate:offline` (needs `SQLITE_URL` in `.env`), then `npm run offline:db-push`. [lib/offlineSync.js](lib/offlineSync.js) reconciles offline rows into the real prod client (never the test toggle) once per server start when not offline (`syncOfflineChangesIfAny` in `app/lib/prisma.js`), or on demand from `/admin/database` ("סנכרון נתוני אופליין"): delta by `updatedAt`, upsert by `id` (both schemas share UUIDs), true last-write-wins (a newer-or-equal cloud row is skipped), one manual `AuditLog` row per synced row, models listed in `SYNCED_MODELS` (`Employee`, `Customer`, `DressModel`, `DressItem`, `Order`, `OrderItem`, `Payment`, `PaymentObligation` — extend it if other models start being written offline). **Before re-enabling offline mode on any machine, read "Offline-sync prod-corruption bug fixed (2026-09-09)" in the journal.**

### Automatic audit logging
The same client wraps `create`/`update`/`delete` of every model in a query extension that writes an `AuditLog` row (entity type/id, `changesJson`, and the acting `employeeId` from the verified auth cookie). `AuditLog`, `PageVisitLog`, `Shift` and `BackupRun` are excluded to avoid recursive/noisy logging (after merge of `feature/a5-clean-2026-09-29` also `SearchHistory` and `SavedSearch`); `Employee` `password`/`pinHash` values are masked. Give a write a meaningful history action with `prisma.x.update(auditAs('CANCEL_RENTAL', { where, data }, changes))` (empty `changes` = no row). `upsert`, `createMany`, `updateMany`, `deleteMany` and raw SQL bypass the extension — only there is a hand-written `AuditLog` row legitimate (ESLint `no-restricted-syntax` blocks `auditLog.create` elsewhere; legitimate cases carry an `eslint-disable-next-line` with the reason). Inside `prisma.$transaction(async tx => …)` the audit row is written through the same `tx`. Because of this, bulk data fixes are usually better done through raw SQL or scripts than through Prisma writes, to avoid flooding the audit log.

### Data model ([prisma/schema.prisma](prisma/schema.prisma))
- `Customer` → `Order` → `OrderItem` → `DressItem` → `DressModel` (a `DressModel` is a dress design; a `DressItem` is a physical, barcoded unit of it; an `OrderItem` links a rented unit to an order and tracks its own rental lifecycle: `isTaken`/`isReturned`/`returnedOk`/dates).
- `Order` → `Payment` / `Refund` / `PaymentObligation` (obligations are the itemized charges derived from `PriceList`/`PriceRule`; payments/refunds settle them).
- `Employee` → `Shift` (punch clock), `Department` (role), `Notification` (internal messaging with per-recipient read/archive state via `NotificationTag`).
- `SystemSetting` (key/value rows, one set per org DB) drives most runtime toggles — check it before assuming a feature is hardcoded.
- Almost every model has `legacyId` (unique) — the ID from the original Microsoft Access database this system replaced. Most models soft-delete (`isDeleted`) instead of hard-deleting.
- Data traps: `Order.status` is NULL for almost every order (the real status is computed by `lib/orderStatus.js`); `Order.eventDate` is stored both as UTC midnight and as 21:00/22:00 UTC (legacy imports); on the main gemach ~57% of `OrderItem.dressItemId` is NULL (reach the model through `OrderItem.barcodePrefix`).

### Routing/structure conventions
- App Router: pages under `app/<feature>/`, matching API routes under `app/api/<feature>/route.js`. Path alias `@/*` maps to the repo root (`jsconfig.json`).
- Shared code lives in `app/lib/` (Next-coupled: `prisma.js`, `nedarim.js`, …) and `lib/` (framework-agnostic business logic) — check both when looking for a utility.
- Print views are standalone routes under `app/print/` (`order`, `alterations`, `delivery-courier`, `delivery-bag`), not modals; shared `@media print` rules live in `app/globals.css`; HTML written into a `window.open` popup must not use theme CSS variables. Since 2026-10-01 every print route has its own server `layout.js` (`<PageGate pageKeys=…>`) and `POST /api/pdf` + `GET /api/print/missing-dresses` check the same keys — the page→key map lives in ONE place, [lib/printAccess.js](lib/printAccess.js) (`PRINT_*_PAGE_KEYS`, any-of via `canOpenAnyPage` in `lib/permissions.js`); a new print route must be added there, never gated by login alone. `/api/pdf` `html` mode runs Chromium with JavaScript off and only `data:` + Google Fonts network allowed (`isAllowedHtmlModeRequest` in `lib/pdf.js`). NOTE: the data APIs the print pages fetch (`/api/deliveries`, `/api/alterations`, `/api/orders/[id]`, …) are still login-only — gating the page closes the UI, not a direct API call.
- `middleware.js` only forwards `x-pathname` (for the kiosk exemption in `app/layout.js`); authorization happens per API route (`checkAuth`) and per page tree (`layout.js` + `PageGate`).

### Auth & sessions (auth cookie forgery and privilege escalation fixes)
- Cookies: `auth_token` (employee UUID; legacy, still read in many places) plus `auth_session` (HMAC-signed employeeId + roleId, issued at login by `issueSessionCookie`, secret `AUTH_SECRET`). **Every server-side read of `auth_token` goes through `getVerifiedAuthCookie()` ([lib/authTokens.js](lib/authTokens.js)) or `getSessionEmployee()`/`checkAuth()` ([lib/auth.js](lib/auth.js)) — never `cookieStore.get('auth_token')`** (until 2026-09-20 anyone could paste a UUID into devtools and become that employee).
- Gates: `checkAuth()` = a logged-in employee, or anyone while the `require_login` setting is off (fails open on DB errors); `checkAuth('<role>')` = role required, fails closed; `checkAuth(role, { forceDb: true })` re-checks the DB for sensitive/irreversible writes; `checkPageAccess(roles)` for manager pages. Roles: 0 הנהלה ראשית, 1 מנהל (branch manager), 2 מתכנת; `HEAD_MANAGEMENT_ROLES = [0, 2]`, `DEVELOPER_ONLY_ROLES = [2]`; `roleRank`/`canManageRoles` — an actor may only create/edit employees and assign roles at or below their own rank. A demoted employee keeps role gates for up to 15 minutes (`SESSION_FRESH_MS`).
- Employee joins use `SAFE_EMPLOYEE_SELECT` ([lib/safeSelect.js](lib/safeSelect.js)) — never `include: { employee: true }` (it ships bcrypt hashes and the plaintext passwords of legacy accounts). Match `legacyId` only for digits-only input (`/^\d+$/`) — a UUID that starts with digits otherwise matches another employee.
- `/customer-interface/*` (kiosk) and the punch clock are exempt from the login wall (`isPublicKiosk`/`isPunchClock` in `app/layout.js`); a throw-away page under `/customer-interface/` can render client components for a credential-free browser check — delete it afterwards.

### Permissions system (`/admin/permissions`) — standing rule
- [lib/permissionsMetadata.js](lib/permissionsMetadata.js) — `PERMISSION_CATALOG`: every permission-able page/feature with its Hebrew label, type (`boolean`/`number`), `enforced` flag (`false` = documentation only; the old hardcoded check named in its `note` still governs, so flipping it requires migrating that code first), `approver` flag and plain-Hebrew `userNote`. `ALWAYS_ALLOWED_ROLE_IDS` (0 הנהלה ראשית, 2 מתכנת) pass every boolean item; `notConfigurable` items (admin, employees, pricelist, dashboard, home, kiosk, punch clock, …) are hidden from the wizard.
- [lib/permissions.js](lib/permissions.js) — resolution and mutation (`setDepartmentPermission`/`setEmployeeOverride`) against `DepartmentPermission` (keyed by `Department.roleId`, matching `Employee.roleId`) / `EmployeePermissionOverride`, identical everywhere: always-allowed roles → the employee's own override (allow or block) → the department's explicit value → the catalog default. `hasPermission`, `getEmployeeEffectiveValue`, `getEffectiveValueForEmployees`, `canOpenPage` (every gated `layout.js` via [app/components/PageGate.js](app/components/PageGate.js)), `resolvePageAccess` (sidebar, AI widget), `checkAiAccess()` (every `app/api/ai/**` route); 8 s server cache (`invalidatePermissionCache`).
- [/admin/permissions](app/admin/permissions/page.js) shows ONLY explicitly created rows (`PermissionPageGroup`, built with the 5-step [PermissionRowWizard.js](app/components/permissions/PermissionRowWizard.js)); a key's real values are the OR of every row containing it (`syncKeys` in [lib/permissionPageGroups.js](lib/permissionPageGroups.js)), so a new catalog item is invisible there until someone creates a row for it. Personal exceptions live on the employee card ([EmployeePermissionsPanel.js](app/components/permissions/EmployeePermissionsPanel.js) on [app/employees/[id]/page.js](app/employees/[id]/page.js)); an item owned by a row is read-only on the card.
- **Every enforced boolean item defaults closed** (`defaultForRoleId: () => false`, since 2026-09-22); explicit `DepartmentPermission` rows reproducing the earlier access were written to both PROD DBs — don't delete or "clean up" them without reading [docs/permissions-settings-mapping-2026-09-22.md](docs/permissions-settings-mapping-2026-09-22.md).
- `page:*` decides who can OPEN a page and see its link — it is not an API firewall (the refund APIs stay open to logged-in staff because the order card uses them). All user-facing text on this page is plain Hebrew (no file names, routes, code terms or English).

**Standing rule**: any new access-control decision that varies by department or by individual employee — a new feature flag, a new restricted page, a new "who can override X" exception, a new "an employee types a password to approve X" step — must be added to `PERMISSION_CATALOG` and be readable/editable from `/admin/permissions`, not hardcoded as a fresh `roleId` array or a fresh one-off `Employee` boolean column (`Employee.showAi`/`canReportErrors` are retired, unused columns — never re-introduce a per-item checkbox). A single global on/off (no per-department variation) still belongs in `SystemSetting` as before — this system is specifically for the "which department/which employee" dimension. Approvals are catalog items with `approver: true`: client `window.customAuthPrompt(msg, 'feature:<key>')` → `/api/auth/verify-pin` → the route that records the action re-checks server-side (`hasPermission`, or `verifyManagerPin(id, pin, key)`); never add a fresh `roleId === 1 || roleId === 2` approver check. **When migrating a hardcoded gate, grep for every call site of the old check** (duplicates exist — the `orderDate` PIN gate lived in both `ModernGeneralDetails.js` and `ModernInfoTab.js`) and add the matching server-side check: a client dialog alone doesn't stop a direct API call. History: journal entries "Permissions — …", [docs/permissions-security-audit-2026-09-20.md](docs/permissions-security-audit-2026-09-20.md), [docs/permissions-wiring-audit-2026-09-22.md](docs/permissions-wiring-audit-2026-09-22.md).

### ID display rule (from AGENTS.md)
When referencing entities (Orders, Customers, Dress Models, etc.) in code, UI, or communication with the user, always use the human-readable short ID (`orderId`, `legacyId`, `barcodePrefix`), never the internal UUID `id` — except where a route genuinely requires the UUID (e.g. `/customers/[id]` uses the UUID; `/orders/[id]` uses the numeric `orderId`).

### Legacy Access data import
The owner still edits the original Microsoft Access file in parallel with the live app, so [scripts/import_from_access.js](scripts/import_from_access.js) is a **permanent, reusable** full-reload/upsert tool (never delete-then-insert; org2's copy is `scratch/import_new_gemach.js`) — re-run it whenever the Access file has new data. `node scripts/import_from_access.js` dry-runs (counts only); `--write` writes to PROD. Field mappings, the data-quality guards (Hebrew-date parsing via `lib/hebrewDate.js`, null-date sentinels) and the CRASH-SAFETY FIX (2026-08-06) are documented in the script's header comment — read it before re-running the tool or touching the mapping. Known limitation: `OrderItem`/`Payment`/`PaymentObligation` rows are only inserted for orders that have zero rows of all three types; orders with any existing sub-record are left untouched (the header explains why). Rows removed from Access stay active in Postgres; both import scripts end with a `DressItem ORPHANS` report (report-only). The tools finish with [scripts/normalize_legacy_rental_flags.js](scripts/normalize_legacy_rental_flags.js) (owner-approved 2026-09-20): OrderItems the old Access left `isTaken=false` despite a barcode + `takenDate` (R1) or being returned (R2) get `isTaken=true` — never inventing dates, never touching deleted items/orders or `DressItem.location`, idempotent, with a manual `AuditLog` row per item (raw SQL bypasses the audit extension). Standalone: `node scripts/normalize_legacy_rental_flags.js --org=1|2` (dry-run; `--write --expect-host=<host prefix>` to apply); documented at `/admin/access-import`. `node-adodb` needs the Access file's 8.3 short path and only works from PowerShell here.

## Standing rules
Distilled from the incidents in the journal; each one is still in force.

### Data & database
- Keep reads outside interactive `prisma.$transaction(async tx => …)`: only writes plus a cheap re-check inside (heavy reads blew Prisma's 5 s default against remote Neon); a transaction that must do more passes explicit `{ timeout, maxWait }`.
- No hand-written `AuditLog` row next to a normal Prisma write (the extension already logs it and the history shows a duplicate) — use `auditAs()`; manual rows only where the extension can't see the write (`updateMany`, `upsert`, raw SQL).
- Never filter `Order.status` with a bare `NOT IN` / `<>` / Prisma `notIn` — NULL rows silently drop out (the kiosk showed booked dresses as free; AI counts were ~99% short). Compute status with `lib/orderStatus.js`; in SQL use `COALESCE("status",'')`.
- Don't fork availability logic: the single-model and bulk paths both go through `buildBookingsWhere` in `lib/inventory.js`.
- Hot paths read `SystemSetting` through `lib/settingsCache.js`, not a fresh query per request.
- A missing or empty `SystemSetting` row must keep the pre-change behaviour (the main gemach relies on this for features requested by Neve Yaakov, e.g. the swap/refund policy settings).
- `handleSave` in `app/orders/[id]/page.js` sends `putOrder(...)` an explicit field list — a new editable order field must be added there or it never reaches the server.
- Any code path that assigns a barcode to an order item goes through `lib/rentalBarcodeGuard.js`; a button that unlocks item editing must never sit inside a column a setting can hide.
- Barcodes: a valid barcode is exactly 7 digits on both gemachs (order ids are 5, phones 9+). Quick return (`/api/returns/scan`, old-design `TopbarSearch`, new-design `MenuSearchPanel` with 7 digits + Enter) matches `OrderItem.barcode` only - never fall back to `DressItem.dressBarcode` (open items can share a unit) - and always explains a miss (`reason`: already_returned / not_taken / unknown). See docs/journal-2026.md -> "Quick return by barcode".
- Access imports are upsert-only; orphaned rows are marked `notInUse=true` with a manual `AuditLog` row, never deleted.
- Schema changes: apply the additive DDL by hand to BOTH PROD DBs before the code deploys (`prisma db push` writes only to the one DB in `DATABASE_URL`); generate it with `prisma migrate diff --from-url <db> --to-schema-datamodel prisma/schema.prisma --script` and re-run the diff until it is empty. org2 has fallen behind before (P2022 errors on live pages).

### Dates & time
- Servers run in UTC; Israel is UTC+2/+3. Day windows: `getIsraelDayRange(dateStr)`; "today": `getIsraelTodayDate()` (local-midnight `Date`, for Hebrew-date display) / `getIsraelTodayKey()` (`YYYY-MM-DD`, for inputs/quick dates, with `addDaysToDateKey`) / `getIsraelTodayRange()` (UTC window for queries); "days until/since": `getIsraelDaysUntil(date)`; calendar-day anchors for date math and grouping: `toIsraelCalendarDate()` (all in `lib/hebrewDate.js`) — never `setHours()` windows or `toISOString()` day slices. Test: `node scripts/test_israel_dates.mjs` (simulates 00:30 Israel time and both DST changes under several `TZ` values).
- AI date context is computed by the server (`getIsraelNow`/`buildDateContext`, macros `HEBREW_MONTH_START/END('ELUL', 5786)`), never by the model. Vercel Cron schedules are fixed UTC, so Israel-time send hours shift with DST.

### Settings & the two orgs
- **Code fixes ship to both orgs; settings and business rules are per org.** For any new `SystemSetting` requested by one org (standing procedure): create the key/row in BOTH DBs at the same time (identical keys keep both settings panels structurally identical), set the requested value only for the org that asked, and give the other org the value that preserves its current behaviour (usually the code-documented off/default). Consistency means identical keys, never identical values. Sole exception: `agent_digest_email_*` exist on org1 only. Within a tab, list new keys in `SETTINGS_ORDER` (`app/admin/settings/SettingsClient.js`).
- A feature built for one org ships behind a `SystemSetting` whose default keeps the old behaviour — unguarded org2 features have leaked to org1 before (the batch print-prep option, 2026-09-16).
- Any script that writes `SystemSetting` rows (or other data) meant for one org verifies the target host before writing (`if (!host.startsWith('<expected host>')) throw …`, the pattern of `scratch/write_new_gemach_settings.js`); never rely on whichever `.env` happens to be active.
- DB hosts move (Neon branch cutovers, a new project after an outage). After any connection change, re-read rows you wrote directly earlier from the *current* env (`scratch/new_gemach_db.env` for org2, `.env` for org1) before relying on them; whoever performs a cutover re-applies direct writes made after the snapshot was taken.
- Delivery-related reports come from Neve Yaakov (`enable_deliveries` is off on org1) — read both orgs' live settings before deciding which org a report is about.

### Automated AI agent: hard ban on changing inventory-calculation SystemSettings
The automated AI agent (fix-reports GitHub Actions run, or any other unattended/scheduled agent) must never change the *value* of these `SystemSetting` keys, in either org, under any circumstances — not even as a one-line fix for a reported bug. If a reported issue seems to require it, the agent stops, explains why in its reply (`--question`) and leaves it for Moshe: `inventory_buffer_days`, `inventory_skip_weekends`, `inventory_hold_minutes`, `inventory_include_warehouse`, `allow_renting_reserve_items`, `hide_custom_spacing`, `enable_rental_extension` (all feed `lib/inventory.js`'s availability/overlap calculation). Order-status/display settings such as `draft_orders_show_as_deleted` are not covered. This is a hand-picked list — a future setting that changes date/day/hold math for inventory must be added here explicitly.

### Permissions & auth
- New department/employee access decisions go into `PERMISSION_CATALOG` (see the standing rule above); every client-side gate, PIN dialogs included, needs its server-side twin.
- `getVerifiedAuthCookie()` for every `auth_token` read, `SAFE_EMPLOYEE_SELECT` for every employee join, `legacyId` lookups for digits-only input only.
- Never type a password into a live site — use `/api/dev/agent-login` (or an API key after merge).

### AI
- `normalizeAiSql` runs after `processHebrewDateMacro` in every AI route; use the `HEBREW_MONTH_START/END` macros instead of `eventDateHebrew LIKE` (that column stores day letters without gershayim).
- Never reach the model number through `DressItem` (use `OrderItem.barcodePrefix`); never JOIN `OrderItem` when only counting orders.
- Keep `data` as the rows field of `/api/ai` — renaming it breaks `AIFloatingWidget`, `app/page.js`, `admin/ai` and `customer-interface` together.

### Vercel, Neon & background work
- The real budget is Neon Free's 5 GB data transfer per project per month (org1 went down on it 2026-09-18) and Vercel invocations — weigh every background job and full-table read against it.
- Background polling uses a `?light=1` endpoint, at least 120 s, pauses while the tab is hidden, and is not logged (the visit-log interceptor skips `light=1`). `/api/log-visit` is batched — never add a per-call `fetch('/api/log-visit')`.
- The function region is a per-project Vercel setting (org1 `iad1`, org2 `fra1`), not `vercel.json`; if a DB changes region, update the project and re-check `/api/health`.
- Await all async work (emails, logs) before a route returns — Vercel may freeze the invocation after the response.
- Routes that call the Apps Script/Drive bridge set `export const maxDuration = 60` (Hobby's 10 s default kills a cold bridge round-trip).

### Git, worktrees & the Windows environment
- The repo sits in the Google-Drive-synced Desktop; Drive plants `desktop.ini` files, and those inside `.git` break git (`fatal: bad object refs/desktop.ini`, "did not send all necessary objects", "ignoring broken ref"). Fix: `find .git -iname desktop.ini -delete`; keep `attrib +S` on the top-level `.git` folder only — never recursively (it blocks git's own deletes). Fetch workaround: `git fetch origin main --no-tags --negotiation-tip=HEAD`.
- `origin` is SSH (`git@github.com:moshehik/gemach-app.git`); if HTTPS "Connection was reset" errors reappear, check `git remote -v` first.
- Working-tree files are CRLF (`core.autocrlf=true`) and a few are CRLF in the index too (`git ls-files --eol`) — preserve line endings when editing.
- A script run from a worktree whose `node_modules` is a junction gets the main checkout's `.env` injected by Prisma — export `PROD_DATABASE_URL` explicitly when targeting another DB.
- Verify findings against `origin/main` in your own worktree, not the shared checkout (it is usually on another session's branch); judge a branch by its diff against `main`, not by its commit count.

- Don't guess undefined business rules (e.g. "50% partial payment on model replacement", or when to create the Nedarim הוק) — ask.
