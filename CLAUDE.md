## What this is

A Next.js (App Router) management system for a "gemach" (גמ"ח) — a free-loan society that lends out wedding/event dresses. It tracks customers, employees, dress inventory (models + physical items), rental orders, payments/refunds, price lists, work shifts, and internal messaging. UI and data are Hebrew, RTL.

## Commands

Run from `gemach-app/` (this is the actual app root; the parent folder contains unrelated legacy Access-migration scratch files and is not part of the app).

```bash
npm run dev      # next dev --webpack
npm run build     # prisma generate && next build --webpack
npm run start
npm run lint      # eslint
```

There is no automated test suite (no Jest/Vitest configured). Verification is done by running one-off scripts (see below) or manually through the dev server. `eslint.config.mjs` ignores `*.js` at the repo root, `scripts/**`, and `scratch/**` — these are ad-hoc/throwaway scripts, not part of the linted app.

The repo root is cluttered with many one-off `check_*.js`, `fix_*.js`, `test_*.js`, `migrate_*.js`, `scratch_*.js` scripts used historically for data migration/debugging against the DB directly. They aren't part of the app runtime — don't treat them as source of truth for current behavior, and don't add new throwaway scripts there; prefer `scratch/` (gitignored) for anything temporary.

## Architecture

### Dual/offline database mode
[app/lib/prisma.js](app/lib/prisma.js) exports a `Proxy` that routes every Prisma call to either a "prod" or "test" Postgres client based on the `.active-db` file (or `globalForPrisma.activeDbMode`) — toggled via `/app/api/admin/database`. There is also an `IS_OFFLINE_MODE` env flag that swaps in a locally generated `@prisma/local-client` (SQLite, schema is [prisma/schema.local.prisma](prisma/schema.local.prisma) — `prisma/schema-sqlite.prisma` is an unrelated, stale, unused file despite the similar name, don't confuse the two) for working without internet. Always import the shared client from `@/app/lib/prisma` — never instantiate `PrismaClient` directly.

The local client isn't generated automatically by `npm install`/`npm run build` (that would make Vercel builds depend on a `SQLITE_URL` env var they don't need) — run `npm run generate:offline` once on any machine that will actually use offline mode (needs `SQLITE_URL` in `.env`), then `npm run offline:db-push` to create the local SQLite tables. Rows written offline get reconciled back into Postgres by [lib/offlineSync.js](lib/offlineSync.js) — a simple delta sync keyed by each model's `updatedAt`, upserting by `id` (both schemas use the same UUIDs, so no id remapping is needed) with true last-write-wins conflict handling (the cloud row's own `updatedAt` is checked before every upsert; a newer-or-equal cloud row is skipped, not overwritten — see the 2026-09-09 incident below for why this matters) plus a manual `AuditLog` entry per synced row. It runs automatically once per process on server startup whenever `IS_OFFLINE_MODE` is not `'true'` (see `syncOfflineChangesIfAny` in `app/lib/prisma.js`), and can also be triggered on demand from `/admin/database` ("סנכרון נתוני אופליין") without restarting the server. Currently covers `Employee`, `Customer`, `DressModel`, `DressItem`, `Order`, `OrderItem`, `Payment`, `PaymentObligation` (`SYNCED_MODELS` in `lib/offlineSync.js`) — extend that list if other models start being written while offline. **Before re-enabling offline mode on any machine, read the 2026-09-09 incident section below first.**

### Automatic audit logging
The same Prisma client wraps every model's `create`/`update`/`delete` in a query extension that writes an `AuditLog` row (entity type/id, diffed `changesJson`, and the acting `employeeId` pulled from the `auth_token` cookie). `AuditLog`, `PageVisitLog`, and `Shift` are excluded to avoid recursive/noisy logging. Because of this, bulk data fixes are usually better done through raw SQL or scripts than through Prisma writes, to avoid flooding the audit log.

### Data model ([prisma/schema.prisma](prisma/schema.prisma))
Core entities and relations:
- `Customer` → `Order` → `OrderItem` → `DressItem` → `DressModel` (a `DressModel` is a dress design; `DressItem` is a physical, barcoded unit of that design; `OrderItem` links a rented unit to an order and tracks its own rental lifecycle: `isTaken`/`isReturned`/`returnedOk`/dates).
- `Order` → `Payment` / `Refund` / `PaymentObligation` (obligations are the itemized charges derived from `PriceList`/`PriceRule`; payments/refunds settle them).
- `Employee` → `Shift` (punch clock), `Department` (role), `Notification` (internal messaging with per-recipient read/archive state via `NotificationTag`).
- Almost every model has `legacyId` (unique) — a carry-over ID from the original Microsoft Access database this system replaced, used to cross-reference during/after migration. Most models also have soft-delete (`isDeleted`) rather than hard deletes.

### Business logic lives in `lib/`, not in routes
- [lib/pricingEngine.js](lib/pricingEngine.js) — recalculates `PaymentObligation`s for an order; explicitly ports logic from the legacy Access VBA module `שמלות_תשלום_רישום`.
- [lib/inventory.js](lib/inventory.js) — dress item availability/overlap logic, including `addDaysSkippingWeekends` for rental-period spacing between bookings.
- [lib/orderStatus.js](lib/orderStatus.js) — derives an order's Hebrew status string (`הוחזר`, `הושכר חלקי`, `מחוק`, etc.) from its items' taken/returned flags — this is the source of truth for order status, don't duplicate the logic in components.
- [lib/hebrewDate.js](lib/hebrewDate.js) and the `@hebcal/core`/`hebcal` deps — Hebrew calendar conversions, used throughout order/event dates alongside Gregorian dates (`Order.eventDate` + `eventDateHebrew`).
- [lib/ai/gemini.js](lib/ai/gemini.js) — Gemini API integration backing the AI search/chat features (`AIChatSession`, `AISearchBar`, `AIFloatingWidget`); keys come from `GEMINI_API_KEYS` in `.env.local`.

### Routing/structure conventions
- App Router: pages under `app/<feature>/`, matching API routes under `app/api/<feature>/route.js`.
- Path alias `@/*` maps to the repo root (`jsconfig.json`).
- Shared client code lives in `app/lib/` (Next-coupled: `prisma.js`, `nedarim.js`) and `lib/` (framework-agnostic business logic) — check both when looking for a utility.
- Print views are separate routes under `app/print/` (e.g. `app/print/order`, `app/print/alterations`) rendered standalone for printing, not modals.
- Auth is a simple cookie (`auth_token` = employee UUID) gated by the `require_login` `SystemSetting`; see [lib/auth.js](lib/auth.js). `SystemSetting` (key/value rows) drives various runtime toggles — check there before assuming a feature is hardcoded.

### Permissions system (`/admin/permissions`) — standing rule
Access control used to be ad-hoc: a hardcoded `roleId` array copy-pasted into whichever route/page needed a gate, plus one-off flat booleans on `Employee` (`showAi`, `canReportErrors`) for individual exceptions — no single place showed which departments could do what, or why. [/admin/permissions](app/admin/permissions/page.js) is now that single place, backed by:
- [lib/permissionsMetadata.js](lib/permissionsMetadata.js) — the catalog: every permission-able page/feature, its Hebrew label, its type (`boolean`/`number`), and an `enforced` flag (`true` = a real runtime check reads it; `false` = the admin page records the *intended* access for documentation, but the actual gate is still the old hardcoded roleId check named in that item's `note` — flipping `enforced` to `true` requires doing that code migration first, not just editing the flag).
- [lib/permissions.js](lib/permissions.js) — resolution (`getEmployeeEffectiveValue`/`hasPermission`, and the `getEffectiveValueForEmployees` batch form for lists) and mutation (`setDepartmentPermission`/`setEmployeeOverride`) against the `DepartmentPermission` (keyed by `Department.roleId`, matching `Employee.roleId`'s own relation to `Department`) and `EmployeePermissionOverride` tables. An employee's effective value = their own override, else their department's explicit value, else the catalog item's `defaultForRoleId` (chosen to match whatever the old hardcoded check already did, so turning this system on changes nothing until an admin edits something).
- [app/components/permissions/EmployeePermissionsPanel.js](app/components/permissions/EmployeePermissionsPanel.js) — the one per-employee override UI, embedded both in the admin page's employee picker and directly on an employee's own card ([app/employees/[id]/page.js](app/employees/[id]/page.js)), so the two can't drift apart.
- The `PermissionPageGroup` model (see its doc comment in `prisma/schema.prisma`) — named, admin-created rows in ONE unified table on `/admin/permissions` (pages and features may be mixed in the same row), created/edited through the 5-step wizard [app/components/permissions/PermissionRowWizard.js](app/components/permissions/PermissionRowWizard.js). **Each row stores its own `access` ({roleId: bool}) and `employeeIds`; a catalog key may sit in SEVERAL rows, and its real `DepartmentPermission` / `EmployeePermissionOverride` values are the union (OR — lenient) of every row containing it, re-derived on every create/update/delete by `syncKeys` in [lib/permissionPageGroups.js](lib/permissionPageGroups.js).** The table shows ONLY rows that were explicitly created — never seeded, no implicit row for an ungrouped key — so adding a new `PERMISSION_CATALOG` item does NOT make it visible on `/admin/permissions` by itself: create a row for it via "שורת הרשאה חדשה". A key in no row has no explicit values (catalog default), which is also what deleting its last row restores. (`PermissionPageGroup.catalogGroup` is a deprecated, unused column since the pages/features tables were merged.)

**Standing rule going forward**: any new access-control decision that varies by department or by individual employee — a new feature flag, a new restricted page, a new "who can override X" exception — must be added to `PERMISSION_CATALOG` and be readable/editable from `/admin/permissions`, not hardcoded as a fresh `roleId` array or a fresh one-off `Employee` boolean column. A single global on/off (no per-department variation) still belongs in `SystemSetting` as before — this system is specifically for the "which department/which employee" dimension. As of 2026-09-17 only four items are actually `enforced: true` (`feature:ai`, `feature:error_reports`, `feature:debt_approval`, `feature:export_max_rows`); the `page:*` items are documented-only placeholders — migrating each page's `layout.js` gate to read from here (and flipping its `enforced` flag) is deliberately left as separate future work, not done in this pass.

**`/admin/permissions` redesign — shipped 2026-09-20 (branch `redesign/permissions-ui`, merged to `main`).** Reached from the developer-only `/admin/site-settings` sidebar ("הרשאות" entry, `SettingsClient.js` `mode="developer"`) as well as the existing card on `/admin/site`. Behavior worth knowing before touching it again:
- **One unified table ("שורות הרשאה") starting EMPTY, by owner's decision** — pages and features together, rendered by `PermissionGroupTable` in [PermissionsClient.js](app/admin/permissions/PermissionsClient.js). No seed/backfill script exists (the old `scripts/backfill-permission-groups.js` was deleted). Empty means "catalog defaults", not "off" — the four `feature:*` items stay `enforced: true` and resolve to `defaultForRoleId`. Saving a row that contains a feature DOES change real behavior immediately; `page:*` items stay documented-intent only (`enforced: false`, shown with a "מתועד בלבד" badge).
- **5-step wizard** (`PermissionRowWizard.js`): 1 שם → 2 עמודים/פיצ'רים → 3 מחלקות → 4 עובדים ספציפיים → 5 אישור. Steps 1-2 must validate before moving on; when editing, all steps are reachable at once. Step 3 shows a "מותר כיום / לא מותר כיום" badge per department (the catalog default for the selected items) plus select-all / clear / reset-to-defaults, and a new row's toggles start from the first added item's default so saving can't silently revoke today's access. Step 4 explains and can be skipped (items that don't support per-employee overrides are called out). Step 5 is a read-only summary with warnings: row contains enforced features (takes effect immediately), enforced feature with nobody allowed (blocks everyone but the programmer), documented-only pages, items shared with other rows. **"מחק שורה"** (edit mode) deletes for real — each of its items not in another row returns to the catalog default (its `DepartmentPermission` values and row-made overrides are cleared).
- **Item display** ([ItemInfo.js](app/components/permissions/ItemInfo.js)): every page/feature label is followed by an info icon whose popover explains it (description, enforced vs documented-only, what governs it today) and, for pages, the label itself is a link (no underline) opening the page in a NEW TAB. **All user-facing text on this page must be plain Hebrew** — no file names, code terms, English or route paths (owner feedback 2026-09-20): labels carry no `(/route)` suffix, and the popover shows the catalog's `userNote` (plain-language), never the developer-facing `note`. The old inline iframe preview (eye button) was removed — it rendered a blank white window. An item that sits in 2+ rows is **highlighted** (warning chip + link icon, names of the other rows in the tooltip) and, being a union, is open if ANY of its rows allows. Number-type items (`feature:export_max_rows`) are not offered in rows — no yes/no; legacy-field items (`feature:ai`, `feature:error_reports`) get department access from a row but no per-employee override.
- **הנהלה ראשית (roleId 0) and מתכנת (roleId 2) have no toggle** (`ALWAYS_ALLOWED_ROLE_IDS` in [lib/permissionsMetadata.js](lib/permissionsMetadata.js)): they are unconditionally allowed every boolean item — `getDepartmentEffectiveValue` / `getEffectiveValueForEmployees` return `true` for them, `GET /api/admin/permissions` leaves them out of the department list, and `sanitizeAccess` never stores them on a row. What is restricted to the programmer alone is gated by `DEVELOPER_ONLY_ROLES` in `lib/auth.js`, outside this catalog. Side effect (2026-09-20): `feature:debt_approval`'s catalog default excludes roleId 0, so head management gained that approval right when this shipped.
- **Specific employees** show as `EmployeeTag` pills ([EmployeeTag.js](app/components/permissions/EmployeeTag.js)); stored as `EmployeePermissionOverride` rows whose `note` starts with `ROW_OVERRIDE_NOTE_PREFIX` — only those are ever cleared by a row change; a grant made on the employee's own card is left alone.
- **DB changes applied by hand to BOTH gemach databases on 2026-09-20** (additive; Prisma migrations are per-database here): `PermissionPageGroup.catalogGroup TEXT NOT NULL DEFAULT 'pages'` (now deprecated/unused), `access TEXT NOT NULL DEFAULT '{}'`, `employeeIds TEXT NOT NULL DEFAULT '[]'` on org1 (`misty-darkness-06917297` / `ep-weathered-tree-avpypjjr` — the post-outage project, NOT the old blocked `purple-term`) and org2 (`gemach-dresses-2` / `ep-broad-night-b1fxha9e`, host from `scratch/new_gemach_db.env`). Every existing `PermissionPageGroup` row was then deleted on both (owner asked for a fully clean start); `DepartmentPermission` and `EmployeePermissionOverride` were already empty. org2 was also found missing `DressModel.thumbnailUrl` and the `Attachment` table (from the already-merged "remove Vercel Blob" change) — applied too. `prisma migrate diff --from-url <db> --to-schema-datamodel prisma/schema.prisma` was empty on both afterward. **Any future schema change to this model must be applied to org1 AND org2 by hand the same way** (re-read each host from the current `.env` / `scratch/new_gemach_db.env` first — they have moved before).
- **Testing tip:** the app is fully behind login, but `/customer-interface/*` is exempt (see `app/layout.js` `isPublicKiosk`), so a throwaway page under it can render these client components with fake props for a browser check without credentials — delete it afterwards.

One important known limitation: OrderItem/Payment/PaymentObligation are only inserted for orders whose sub-records are entirely missing (zero rows of all three types) as of the current run — not just orders brand-new to the DB this run, since a crash between the Order upsert and the sub-records insert used to make that distinction unsafe (fixed 2026-08-06, see the header's CRASH-SAFETY FIX). ## Windows `desktop.ini` pollution breaks git (2026-09-07)
The repo lives under `C:\Users\moshe\Desktop\גמח שמלות חדש\` — inside the real Windows Desktop folder, not a regular project directory. Windows Explorer periodically writes a `desktop.ini` shell-metadata file into every subfolder it touches there (folder icon/view customization), with no regard for `.git`. When enough of these land inside `.git/refs/**` (e.g. `.git/refs/heads/desktop.ini`, `.git/refs/remotes/origin/desktop.ini`), git's ref-loading treats each stray file as a malformed ref and `git fetch`/`git pull` fails outright with `fatal: bad object refs/desktop.ini` / `did not send all necessary objects` — a hard stop, not a warning.
- **Symptom:** `git fetch`/`pull` suddenly fails with the error above, with no code change to explain it.
- **Fix:** `find .git -iname "desktop.ini" -delete` (safe — these are pure Windows shell metadata, never real git content) then retry. Takes seconds.
- **It comes back:** Explorer regenerates `desktop.ini` continuously while the folder is open/browsed, including inside `app/api/**` route folders (harmless there, just clutter — but the `.git/refs` case is the one that actually breaks things). Don't bother `.gitignore`-ing them one by one; that doesn't stop `.git` internals from getting them too.
- **Real fix, not yet done:** move the project out from under `Desktop` entirely (e.g. `C:\Projects\gemach-app`) so Explorer stops treating every subfolder as a shell-customizable desktop location. Until that happens, re-run the cleanup above whenever `git fetch`/`pull` fails with a `bad object` error.

## Offline-sync prod-corruption bug fixed (2026-09-09)
`syncOfflineChangesIfAny()` ([app/lib/prisma.js](app/lib/prisma.js)) runs automatically on every server start whenever `@prisma/local-client` exists on the machine, and unconditionally upserted every locally-changed row into real Postgres prod via `cloudClient[model].upsert(...)` — with **no check that the cloud row wasn't already newer**, despite `lib/offlineSync.js`'s own comments claiming last-write-wins. A stale, frozen `prisma/gemach-local.db` (an old offline-mode seed last touched ~2026-07-22, never refreshed) got re-synced by a plain `npm run dev` restart and silently reverted ~91 `Employee` rows to that frozen snapshot — plaintext passwords, and for at least 3 employees, `email`/`roleId`/`hourlyWage`/`emailSuffix` too — with **no AuditLog entry**, since `upsert()` isn't one of the operations (`create`/`update`/`delete`) the audit-logging extension recognizes. Worse, `saveSyncState` was only called once at the very end of the full per-model loop, so a failure partway through discarded progress on every model, not just the one that failed — meaning the same stale data got re-uploaded on every subsequent server start.
- **Fixed** in `lib/offlineSync.js`: `syncModel` now `findUnique`s the cloud row and skips the upsert (logs it) when the cloud row exists and its `updatedAt` is `>=` the local row's — true last-write-wins, not blind overwrite. `saveSyncState` now runs after each model inside the loop in `runOfflineSync`, not only once at the end. Each row that IS synced also gets a manual `AuditLog` entry (`{field:{from,to}}` diff + note, `employeeId: NULL`) written directly by `offlineSync.js` itself, since `upsert()` still bypasses the automatic extension. Verified against isolated fake Prisma-like clients in a throwaway script (never against real prod) — no committed test suite exists for this yet.
- **Mitigation** (still in place, machine-local): `prisma/gemach-local.db` was renamed to `prisma/gemach-local.db.DISABLED-corrupting-prod-2026-09-09` so `syncOfflineChangesIfAny()` hits its "local db doesn't exist" catch branch and no-ops. This protects any process on **this checkout**; a different machine with its own separately-generated local client/db is only protected once it also pulls this fix (the fix alone makes even an un-renamed stale file safe to re-sync, since a newer cloud row is no longer overwritten) — the rename is now a belt-and-braces extra, not the only protection.
- **Before deciding to actually use offline mode again**: confirm this fix is deployed/pulled on that machine, then it's safe to rename `prisma/gemach-local.db.DISABLED-corrupting-prod-2026-09-09` back to `prisma/gemach-local.db` (or regenerate fresh via `npm run generate:offline` + `npm run offline:db-push` instead, if the old file's data is no longer wanted). If you don't plan to use offline mode, no action needed — leave it renamed.

Added `restrict_board_to_managers` (a plain `SystemSetting` toggle controlling whether "לוח חודשי" is shown to non-manager employees, added in `app/layout.js`/`app/admin/settings/SettingsClient.js` the same day) directly to org-2's production DB via a one-off scratch script, using `scratch/new_gemach_db.env`'s `PROD_DATABASE_URL`. **Root cause, generalized:** `scratch/new_gemach_db.env`'s `PROD_DATABASE_URL` is not a fixed identity — it gets repointed in place whenever org-2's live database changes host/branch (this has now happened at least twice: see `test-prod-db-urls-collapsed-2026-09-08` memory, and this incident). A direct write via a one-off script targets *whatever host that file resolves to at the moment the script runs*. If org-2's underlying DB is later swapped out (branch cutover, re-clone, disaster recovery, etc.), any row written earlier — even the same day, even by a script with a correct host safety-check at the time — can vanish without any error, because the check passed against the *old* live host, not because anything about the write itself was wrong.

**Standing lesson, for any future Claude Code session (interactive or the automated fix-reports agent) working on this repo:** after any operation that changes org-2's (or org-1's) live database connection — a Neon branch cutover, a DB re-clone, a `DATABASE_URL`/`.active-db` change — do not assume `SystemSetting` rows (or any other data) added via direct scratch scripts *earlier that session or earlier that same day* are still there. Re-verify by reading the row back from the *current* `scratch/new_gemach_db.env` (org-2) or `.env`/`.env.local` (org-1) right before relying on it, rather than trusting an earlier confirmation from possibly-now-stale connection info. If you are the one performing a cutover-style operation, explicitly check for and re-apply any settings/data written directly to the DB (outside of Access reimport) since the snapshot/branch was taken — the wipe+reimport protocol only accounts for Access-sourced data by design, not ad-hoc direct writes like this one.

## Vercel/Neon resource budget — audit + fixes (2026-09-20)
Full writeup: [docs/vercel-resource-audit-2026-09-20.md](docs/vercel-resource-audit-2026-09-20.md). The real ceiling is **Neon Free's 5GB data-transfer per project per month** (the site already went down on it 2026-09-18), not Vercel; treat DB egress and invocation count as the budget when touching anything that runs in the background. Standing rules that came out of it:
- **Function region is a per-project Vercel setting, NOT `vercel.json`.** Both gemachs share one `vercel.json`, but their DBs live in different Neon regions (org1 `gemach-main-prod` = us-east-1 → project region `iad1`; org2 `gemach-dresses-2` = eu-central-1 → `fra1`). A shared `"regions": ["fra1"]` pin made org1 pay ~459ms per `SELECT 1` (org2: 2ms) — measured via `/api/health`. If a DB ever changes region, update that project's `serverlessFunctionRegion` (API `PATCH /v9/projects/{id}`), and re-check `/api/health` `ms`.
- **`/api/log-visit` is batched.** The fetch interceptor in [app/layout.js](app/layout.js) queues entries (`window.__queueVisitLog`) and flushes every ~20s / at 25 entries / on `pagehide` via `sendBeacon`; [app/api/log-visit/route.js](app/api/log-visit/route.js) accepts `{ entries: [...] }` (single-object bodies still work — `app/print/*` send them) and `createMany`s. Never add a per-call `fetch('/api/log-visit')` back.
- **Background polling must use a `?light=1` endpoint and must not be logged.** Convention already used by `/api/error-report?light=1` and now `/api/notifications?light=1` (unread count only); the interceptor skips any URL containing `light=1` (no history row, no `agy_api_call` event). Intervals: notification bell 120s, error-report badge 120s, both pause while the tab is hidden. New pollers: light endpoint + ≥120s + pause-on-hidden.
- **Skipped builds:** `vercel.json` → `ignoreCommand` → [scripts/vercel-ignore-build.sh](scripts/vercel-ignore-build.sh) (exit 0 = skip). Skips `fix-reports/org2-*` preview branches on the main-gemach project, and any commit that touches no build-relevant path (docs/scripts/.github/.claude only; `app/version.json` is excluded because the pre-commit hook bumps it on every commit). **To force a deploy anyway (e.g. a retry after the 100/day rate limit) put `[force-deploy]` in the commit message** — an empty/version-only "trigger a deploy" commit is otherwise skipped now.
- The daily `/api/health` cron was removed (keep-alive is retired; Neon may sleep). The endpoint stays for manual checks.
- **Pointers verified 2026-09-20** (GitHub secrets, Vercel `DATABASE_URL`/`TEST_DATABASE_URL`, local `.env`, all confirmed against the live DBs) and the stale ones fixed — table in [docs/vercel-resource-audit-2026-09-20.md](docs/vercel-resource-audit-2026-09-20.md).
