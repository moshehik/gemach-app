## 2026-10-05: Vercel Fluid Active CPU - shared cache for /api/settings reads in always-mounted components (both gemachs)

- **Cause analysis:** the free-tier CPU alert (75% of 4h) is driven by busy Neve Yaakov working days (4.10: 11.3K API calls, ~600MB JSON for 7 users), not by background polling or the print-center agent (that project now lives in another Vercel account). Details and the measurements: `docs/vercel-cpu-usage-analysis-2026-10-05.md`.
- **Change:** `AIFloatingWidget`, `LegacyErrorReportButton` and `app/rentals/page.js` no longer pull the whole `/api/settings` (~66KB) on every page load - they use the shared 5-minute `apiCache` store (`fetchSharedJson`, `TTL.STATIC`). The new error-report window (`ErrorReportWindow`) is lazy-mounted on first click, so it only reads settings after the user opens it. The store is stale-while-revalidate: an entry older than 5 minutes is still shown instantly and refreshed in the background, so after a settings change made in ANOTHER browser the first read can still be the old value (the next one is fresh); a change made in the same tab invalidates the entry immediately. No behavior or UI change.
- **Expected effect:** the 4.10 count (1,093 `/api/settings` calls at Neve) also includes real saves of the settings screens and the other boot callers, so the saving from these four files is roughly 35-55% of those calls - not all of them. Not yet measured after deployment.
- **Round 2 (same day, branch `perf/cpu-reduction-2026-10-05`):** also moved the remaining raw `GET /api/settings` readers to the same shared cache: deliveries page, messages page, employee card (new + legacy), profile page (new), price-list page. Left raw on purpose: print pages, the public kiosk, login / punch clock, the settings-editing screens, and the frozen legacy copies (`LegacyProfilePage` is blob-pinned by `test_page_variant_switch.mjs`).
- **Server cache for `GET /api/settings` (30s per warm instance, `lib/settingsCache.js getCachedSettingsList`):** same query, same response (BRAND_LOGO / backup_requested_at excluded, category+id order, secret masking and the `non_working_days_extra` note stripping applied per request on top of the cached rows). Dropped on every settings write on that instance (`POST /api/settings`, `POST /api/settings/labels` - which did not invalidate before -, backups/AI-restrictions/fix-loop writers) and on a DB-mode switch. Other warm instances converge within 30s. `?fresh=1` bypasses it - used by the two settings-editing screens (`/admin/settings`, settings-sim). Tests: `node --no-warnings --import ./scripts/cpu-reduction-tests/register.mjs --test scripts/cpu-reduction-tests/settings-get.test.mjs` (old-vs-new response comparison with a mocked prisma). The prisma shim of `scripts/business-days-tests` got the missing `auditAs` export, which un-broke `settings-route.test.mjs`.
- **Boot calls survive a full page reload (per tab, sessionStorage):** `/api/settings`, `/api/settings/labels`, `/api/me`, `/api/me/design-prefs` are kept per tab (`lib/apiCachePersist.js`); the allow-list of these four URLs is the opt-in, so whichever caller asks first (page or layout widget) hydrates and writes. Fresh windows (no request at all): labels and design-prefs 15 min, settings 5 min, `/api/me` 90s; older than the window but under 15 min = shown instantly + refreshed in the background; older is ignored. Keyed to the signed-in employee (`<html data-gm-uid>` from the verified cookie) and, for `/api/me` and design-prefs, the body must carry the same employee id (read and write). Flushed on login/logout, on any write that invalidates the same prefix and on 401/403. Focus refresh of these four is 3 min. Display cache only - the server enforces everything. The legacy `UserMenu` now subscribes to `/api/me` updates. `/admin/bulk-email` and the refund planner read `/api/settings?fresh=1`. Estimated 15-35% of boot calls, to be measured via PageVisitLog. Tests: `scripts/cpu-reduction-tests/api-cache-persist.test.mjs`.
- **Error-report panel list cached for 60s:** the full `GET /api/error-report` (up to ~270KB; 70% of its calls repeated within a minute) is now read through `fetchFreshJson` (`lib/apiCache.js`): opening/closing the window again within 60s makes no request, older is always refetched (never a stale list). Any write to `/api/error-report*` (send, reply, archive, mark read, sketch decision) drops it, and so does a change of the unread counter seen by the 120s light poll (which is unchanged). Tests: `scripts/cpu-reduction-tests/error-report-cache.test.mjs`.
- **Not changed (needs a decision):** the 15-second freshness window of the orders / dresses lists, and the heavy payloads of `/api/dresses`, `/api/inventory/preload`, `/api/error-report`.

## 2026-10-02: Explicit return date on a closed day = the next working day, everywhere (both gemachs)

- **תאריך החזרה מפורש שנופל על יום סגור יוצג כיום העבודה הבא — בכרטיס הזמנה, הדפסה, מייל, רשימת איחורים ולוז.** Owner decision 2.10.2026 ("ההחזרה של אירוע בחמישי תהיה בראשון"). An order whose `toDate`/`returnDate` (abroad / weekday / extra-day orders, Access imports) falls on Friday, Shabbat, a chag, erev chag or a day marked "ללא פעילות" in the calendar is now due on the first working day after it - the same rule the daily schedule (stage 8) already used - so the printed order, the two customer e-mails, the late-return reminder e-mail, the order card's late alert, the quick-return bar, the overdue list, "אמור לחזור מחר" and the "החזרה היום/מחר" search chips all show and count the same date. Example: `toDate` Friday 16.10.2026 is printed/mailed as Sunday 18.10 and is "late" 7 days after Sunday (before: 7 days after Friday, i.e. two days earlier than the schedule). A return date that already falls on a working day is unchanged; regular orders (no explicit date) are unchanged.
- One shared helper, `rollForwardToWorkingDay` (+ its inverse `rolledSourceRange`) in `lib/businessDays.js`, used by `lib/lateReturn.js` and `lib/schedule/dates.js`; `getLateReturnInfo` also returns `dueKey`. The customer's original date is not modified in the database. Files: `lib/businessDays.js`, `lib/lateReturn.js`, `lib/schedule/dates.js`, `app/api/a5/adv/route.js` (SQL window of explicit dates), `app/api/cron/daily/route.js` (e-mail text).
